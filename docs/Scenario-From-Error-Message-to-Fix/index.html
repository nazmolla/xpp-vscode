    Scenario: From Error Message to Fix¶

    This walkthrough is for developers who get an error message from a user, a batch job log or an integration, and need to find where it comes from, why it happens and how to fix it. Functional consultants can follow phases 1 and 2 (or use the F&O Functional Triage agent) to decide whether the cause is setup, data or code.

    The situation¶

    A user reports: "When I create a customer I get Field 'Customer group' must be filled in." At the same time, the nightly import of web shop customers, a custom class ContosoCustomerImport in the ContosoExtensions model, logs the same message for some rows.

    Two causes are possible:

    • The platform raises "Field '%1' must be filled in." when a field whose Mandatory property is Yes is empty when the record is saved. On CustTable, the field CustGroup (label "Customer group") is mandatory.
    • Code can raise the same label text for its own checks.

    So the question is: which field is empty, who should have filled it, and is it setup, data or code?

    What you need¶

    Need Why
    A connected environment (Connect-to-Environment) Metadata and the cross-reference database.
    The cross-reference database Find Message Source and Find References use it for where-used.
    The project of the model you will fix (ContosoExtensions) Build, tests and deploy work on the project.
    Database access (optional) To check the data behind the error.
    A UDE to reproduce on, never production Fixes and test data go to development environments only.

    Step by step¶

    Phase 1: Get the exact message¶

    1. Copy the message exactly as the user saw it, values included. Do not retype or translate it. For an integration, copy the text from the log row.
    2. If you can reproduce it while debugging, the message shows in the Infolog view of the F&O Studio panel. Each message has Find Message Source inline and in its context menu. See Infolog.
    3. Note the context: the form (Customers, CustTable), the action (New, then Save), the company and, for the import, the input row.

    Phase 2: Find where the message comes from¶

    1. Run Find Message Source (Dynamics 365 view > Find > Find Message Source…, or the command palette). If you selected the text in an editor first, it is filled in.
    2. Paste Field 'Customer group' must be filled in. and press Enter.
    3. Read the result list. For this message the list has three parts:
    Section What it shows What it means here
    Mandatory fields · platform check Table fields with the label "Customer group" whose Mandatory property is Yes, with the model and whether the table or an extension sets it. CustTable.CustGroup, Mandatory = Yes, set by the table. The platform raises the message when it is empty.
    Code that raises it for "Customer group" Code lines that use the same label for one of those fields. Validation code that checks the customer group itself.
    Same text, other fields Code that reuses the text for other fields. Usually not your case; kept apart.

    Labels whose text matches are listed with their IDs. Placeholders (%1) match any value. 4. Click CustTable.CustGroup to open the table designer on that field. Click a code line to open the X++ code view at that line. 5. If a label shows "Not used in X++ code", the platform raises it, or the package was not built with cross-reference data. If where-used is unavailable, the list says why (for example, no cross-reference database).

    See Find-Message-Source.

    Decision point. The platform check means the record was saved with an empty CustGroup. Now find out who left it empty:

    • A user in the form: data entry or setup (for example a customer template or default that should fill it). Hand it to a functional consultant, or use the F&O Functional Triage agent (below).
    • Code that creates customers: a code defect. Continue with phase 3.

    Phase 3: Find the code that saves the record¶

    1. Find every place your model inserts customers. Run Search Code in All Packages (Ctrl+Shift+Alt+F) with CustTable and insert, or a regular expression such as custTable\.(insert|write)\(. Results list the element, method, line and model. See Search-Code.
    2. Narrow it with Find References on CustTable (right-click in the Application Explorer) and look for elements of ContosoExtensions. The list shows element, member, line and kind. See Find-All-References.
    3. Open ContosoCustomerImport and read the method that builds the customer. In the code view, F12 goes to definitions, and Call Hierarchy shows who calls the method. See Call-and-Type-Hierarchy.
    4. In the example, the method sets AccountNum, the party and the currency, then calls insert() without a customer group when the web shop sends none.

    To see how standard code creates customers with a group, run Find Similar Standard Implementations on your class, or describe the task ("create a customer from code"). See Find-Similar-Implementations.

    Phase 4: Check the data¶

    1. With database access (Database-Access), right-click CustTable and choose Browse Table Data. Filter on the company and sort by the created date to see the last imported customers.
    2. For the rejected rows, open New SQL Query and check the input of the import (your staging or log table). The query panel is read-only by default: one SELECT, always rolled back. See SQL-Query-Panel.
    3. Check which customer group the business wants as default for web shop customers, for example WEB, and that it exists in CustGroup for that company.

    Phase 5: Fix the code¶

    1. Run Start Copilot Checkpoint only if you plan to let Copilot edit. For your own edit, no checkpoint is needed.
    2. In the code view of ContosoCustomerImport, set the customer group before the insert, from a parameter or the input, and stop with a clear message when neither has one. Use a label for the message: the Quick Fix (Ctrl+.) offers extract to label. See Quick-Fixes.
    custTable.CustGroup = _input.parmCustGroup()
    ? _input.parmCustGroup()
    : ContosoWebShopParameters::find().DefaultCustGroup;

if (!custTable.CustGroup)
{
    throw error("@ContosoLabels:WebShopCustomerGroupMissing");
}
    1. Save. Syntax errors show while you type; obsolete APIs are underlined. See Syntax-Check-and-Obsolete-Warnings.
    2. Run Build Project (Ctrl+Shift+B). Errors go to Problems at the right line; a failed build offers Show Problems. See Build-Project-and-Model.

    If the fix belongs in a standard class instead (for example defaulting in a standard method), use Create Code Extension on that class to get a Chain of Command class in your model. See Create-Code-Extension.

    Phase 6: Prove the fix¶

    1. On a UDE, run Deploy Models to Environment. Pick the ContosoExtensions package (preselected) and the database sync (None is enough for a code-only change). Progress shows in the X++ Deploy output. See Deploy-to-Environment.
    2. Try the import for one row with Run Snippet in Environment: write a class with a main method in an untitled X++ editor, then run the command. It saves the code into the scratch class ContosoExtensionsScratchRunner, builds, offers Deploy and Run or Run Without Deploying, and opens the class in the browser. Delete the scratch class afterwards; the Pre-Deploy Checklist fails while it is in the model. See Run-Snippet.
    3. Add a regression test: right-click ContosoCustomerImport and run Generate SysTest Class with Test Data (ATL). It creates ContosoCustomerImportTest with a test per public method and customer data from the Acceptance Test Library, and offers Add References when the model lacks the ATL packages. Write the assert: an import without a group gets the default group. See Generate-SysTest-Class.
    4. Build, deploy, and run Run Tests (or use VS Code's Test Explorer). When the build is newer than the last deploy, F&O Studio warns first and offers Deploy First or Continue. Results go to the X++ Tests output. See Run-Tests.
    5. Ask the user to retry in the UDE, or open the form with Open in Browser on the CustTable menu item.

    Phase 7: Review and hand over¶

    1. Run Review My Changes. It lists the changed elements against xpp.git.baseBranch with their best practice and performance findings and a pull request summary to copy. See Review-My-Changes.
    2. Link the work item with Link Work Item… so the commit message carries it. See Work-Items-and-Pipelines.
    3. Commit and push. Tell the user what changed and what setup the default group needs.

    Doing it with Copilot¶

    Pick the agent by who you are and what you have.

    F&O Functional Triage (read-only, for consultants and key users) turns the report into a cause and a fix in business terms. It uses xpp_find_message_source and, when available, the Dynamics 365 ERP MCP server to look at the record in the environment. If the cause is code, it hands over to F&O Support.

    A user in company USMF gets "Field 'Customer group' must be filled in." when saving a new customer on the All customers form. What is the cause and how does the user fix it? Check the customer templates and defaults too.

    F&O Support (read-only, for developers) finds the condition and where it is:

    The nightly ContosoCustomerImport logs "Field 'Customer group' must be filled in." for some rows. Find where the message comes from, which code in ContosoExtensions saves CustTable without CustGroup, and the exact condition. Check the last imported customers in the database.

    What it does: xpp_find_message_source with the text as shown (it lists the mandatory fields first), xpp_read_object with methodNames for the raising and saving methods, xpp_find_references for callers, and xppQueryData for a read-only SELECT on the UDE after you confirm. Its answer names the cause, the evidence, the fix and how to verify it. Use the handoff Fix in code to switch to F&O Developer.

    F&O Developer implements the fix:

    Implement the fix above in ContosoCustomerImport: default the customer group from the web shop parameters, raise a labelled error when there is none, build, run the best practice checks and open the changed method.

    Before you send it, run Start Copilot Checkpoint and Set Copilot Scope… to ContosoCustomerImport (and the label file). The agent changes code through xpp_update_object, creates the label with xpp_create_label, builds with xpp_build, runs xpp_check_best_practice and opens the method with xppOpenElement.

    F&O Test Engineer writes and runs the regression test:

    Write a SysTest for ContosoCustomerImport with ATL data: an input without a customer group gets the default group, and no default raises the error. Build and run it.

    It builds and runs the test with xppRunTests, which asks before running on the environment and warns when the deployed code is older than the build.

    Checkpoints: - The cause is stated as a condition (field, method, line), not a guess. - Copilot Activity shows only the elements you allowed changed. - The build says BUILD SUCCEEDED and the test passes on the deployed code. - If something went wrong, Revert Copilot Changes Since the Checkpoint… undoes every element, label and project change.

    Checklist¶

    • [ ] The exact message, context, company and record are recorded.
    • [ ] Find Message Source shows the mandatory field or the raising code.
    • [ ] Decided: setup, data or code.
    • [ ] The saving code is found (Search Code, Find References).
    • [ ] The data behind the error is checked.
    • [ ] Fix built without errors; messages use labels.
    • [ ] Deployed to the UDE and verified (Run Snippet or the user).
    • [ ] Regression test added and passing.
    • [ ] Review My Changes clean; work item linked.
    • [ ] Run Snippet's scratch class deleted.
