    Scenario: Debug Standard Code on a UDE¶

    This walkthrough is for developers who need to step through Microsoft's own X++ code on a unified developer environment (UDE) to understand a behaviour, for example where a default comes from, before deciding where to extend it. You set breakpoints in the standard element's code view, attach the debugger from VS Code, trigger the code in the web client and inspect variables, without Visual Studio.

    The situation¶

    A purchasing user asks why a new purchase order gets a delivery address that is not the vendor's. Reading the code helps, but PurchTable defaults many fields from several places. You want to see it run:

    • the init method of the PurchTable form, which runs when the form opens;
    • the initFromVendTable method of the PurchTable table, which copies values from the vendor when you pick one.

    You will set breakpoints in both, create a purchase order in the UDE's web client, and step through.

    If you work on a cloud-hosted or VHD environment instead, the debugger attaches to the local AOS with the C# extension's .NET debugger; see Debugging-on-Cloud-Hosted.

    What you need¶

    Need Why
    A UDE connected with Connect to Environment… It downloads the FinOps tools that contain Microsoft.Dynamics.AX.DebuggerProxy.exe.
    The environment selected in this window (Select Environment…) The debugger signs in to it and asks it for its web client URL.
    The metadata on this machine at the environment's version Breakpoint lines and symbols must match the code the environment runs. Check Environment Application Version tells you.
    A Microsoft account with access to the UDE The debugger proxy uses your Dataverse token.
    A test company and a vendor To create the purchase order.
    A moment when pausing the UDE is acceptable While the debugger is stopped, the environment's server is paused for every user.

    Step by step¶

    Phase 1: Prepare¶

    1. Run Check Environment Application Version. If the environment runs a newer version than your metadata, update it first (the Environment group offers Update Metadata to …). See Version-Drift-Guard.
    2. If you also changed code in your own model, deploy it first with Deploy Models to Environment: the environment runs the code last deployed to it. When the project's build is newer than the last deploy, starting the debugger warns and offers Deploy First or Continue. See Deploy-to-Environment.
    3. In the web client, open the purchase order form once. Code that has run once binds its breakpoints right away.

    Phase 2: Set the breakpoints¶

    1. Press Ctrl+Alt+O, type f:PurchTable and open the form. Right-click it in the Application Explorer and choose View Code to open its X++ code view.
    2. Find the init method (use the Outline view or Ctrl+Shift+O) and set a breakpoint (F9, or click the gutter) on the first line after super().
    3. Open table PurchTable (t:PurchTable) > View Code, find initFromVendTable and set a breakpoint on its first statement.
    4. Set breakpoints in the element's code view. F&O Studio decides which standard elements to load symbols for from the breakpoints in code views when the debugger starts. See Breakpoints-and-Source-Mapping.

    Phase 3: Start the debugger¶

    1. Run Launch Debugger: from the Dynamics 365 view > Debug, from the Infolog view's title bar, or from the command palette. You can also use Run and Debug with the configuration Attach to Dynamics 365 (unified developer environment).
    2. The notification "Preparing X++ debugging…" shows the steps: signing in, then writing debug sources. F&O Studio:
    3. writes the debug source of each element as the compiler numbers it (for forms, with their data source and control classes), so lines match;
    4. for each standard element with a breakpoint, finds the module that holds it and loads only that module's symbols, as Visual Studio does;
    5. starts DebuggerProxy on a free local port, tunnelled to the environment, and attaches to AXHost.exe.
    6. The X++ output lists the standard elements it prepared, for example "Debugging standard code too: PurchTable (…)".
    7. The breakpoints turn solid when they bind. Hollow means the module has not loaded yet: trigger the code.

    See Debugger and Debugging-Standard-Code.

    Phase 4: Trigger the code and step¶

    1. Right-click the PurchTable menu item (or the form) and choose Open in Browser. For a form, F&O Studio finds a menu item that opens it.
    2. The form opens and the debugger stops in the form's init. VS Code shows the stop in the form's code view (not in a separate debug copy). Look at the variables, then continue (F5).
    3. Create a purchase order and pick the vendor. The debugger stops in PurchTable.initFromVendTable.
    4. Use the Run and Debug view:
    5. Variables: this (the purch order buffer), _vendTable, locals;
    6. Watch: add expressions such as this.DeliveryPostalAddress;
    7. Call Stack: who called initFromVendTable, down to the form's data source;
    8. step over (F10), into (F11) and out (Shift+F11), continue (F5).
    9. Step until the delivery address is assigned. Note the method and the condition that set it.
    10. Messages the code writes appear in the Infolog view of the F&O Studio panel. Each message has Find Message Source. See Infolog.

    While the debugger is stopped, the environment's server is paused for every user. Continue or disconnect promptly.

    Phase 5: More breakpoints during the session¶

    • Breakpoints you add or move in the code view of an element prepared at the start, or in your own code, are picked up right away.
    • A standard element that had no breakpoint when you started has no symbols loaded. Stop, set the breakpoint, and start again. Or add its module with additionalModules (phase 7).

    Phase 6: Stop safely¶

    1. Disconnect (Shift+F5) or close the window. F&O Studio resumes the environment first and only detaches; it never ends the environment's process.
    2. A debugger left attached by a VS Code window that crashed is stopped the next time F&O Studio starts.

    Phase 7: Tune the debugger (optional)¶

    The debugger works without a configuration. To change it, add an xpp configuration to .vscode/launch.json (Run and Debug > create a launch.json file > X++):

    {
  "type": "xpp",
  "request": "attach",
  "name": "Attach to Dynamics 365",
  "additionalModules": ["Dynamics.AX.ApplicationSuite.Forms.*.netmodule"],
  "logging": { "exceptions": false }
}
    Option Use
    justMyCode On by default. Turning it off sends every exception the environment throws through the debugger, which can make the environment stop responding. Leave it on.
    additionalModules More modules whose symbols load. Wildcards allowed.
    symbolOptions Replaces the symbol options entirely.
    logging vsdbg logging.
    processName, sourceFileMap Process to attach to (AXHost.exe) and extra source mappings.

    If DebuggerProxy is not in the default location, set xpp.debuggerProxyPath. See Debugger-Options.

    Phase 8: From understanding to change¶

    1. Now you know the method that sets the address. Check who else hooks into it: Go to Implementations (Ctrl+F12) on the method lists overrides, Chain of Command classes and handlers. See Implementations-and-Chain-of-Command.
    2. Find All References (Shift+F12) and Call Hierarchy show the other callers. See Find-All-References and Call-and-Type-Hierarchy.
    3. If the behaviour must change, right-click PurchTable (table) > Create Code Extension and wrap the method. Build, deploy, and debug your wrapper next to the standard code: breakpoints in your own code bind after the deploy. See Create-Code-Extension.

    Troubleshooting¶

    Symptom Cause Fix
    "Select the environment first: F&O Studio: Select Environment." No environment in this window. Run Select Environment….
    "Microsoft.Dynamics.AX.DebuggerProxy.exe was not found." The FinOps tools are not on this machine. Run Connect to Environment…, or set xpp.debuggerProxyPath.
    Breakpoint stays hollow in standard code The code has not run since attach, or the element had no breakpoint when you started. Trigger the code; or stop, set the breakpoint, start again.
    Breakpoint on the wrong line Metadata on this machine differs from the environment's version. Check Environment Application Version, then update the metadata.
    Your own breakpoints don't stop The environment runs an older deploy. Deploy Models to Environment, then debug again.
    The environment hardly responds The debugger is stopped (the server is paused), or justMyCode is off. Continue or disconnect; leave justMyCode on.
    "X++ debugging stopped: …" The proxy or the connection ended. See the X++ output for details.

    Doing it with Copilot¶

    Agents don't drive the debugger. They read code and metadata, so they are useful before and after a session.

    F&O Code Archaeologist (read-only) explains the flow before you debug:

    Explain how a new purchase order gets its delivery address: which methods of the PurchTable form and table and related classes set it, in what order, and from which setup. Give me the methods where I should put breakpoints.

    It reads the methods with xpp_read_object and traces callers with xpp_find_references.

    F&O Support (read-only) turns what you saw into a cause:

    While debugging PurchTable.initFromVendTable I saw the delivery address come from the vendor's delivery location even though the user's site has its own. Read the code path and tell me the exact condition and whether it is setup or code.

    When the change is clear, use Fix in code to hand over to F&O Developer:

    Create a Chain of Command wrapper of PurchTable.initFromVendTable in ContosoExtensions that keeps the site's address when the site has one. Call next first. Build and open the class.

    Checkpoints: - Breakpoint locations come from the code the agent read (method names you can open). - The wrapper calls next. - After deploy, your breakpoint in the wrapper and the standard breakpoint both stop.

    Checklist¶

    • [ ] Metadata version matches the environment.
    • [ ] Own code deployed (if any).
    • [ ] Code run once in the web client.
    • [ ] Breakpoints set in the code views of the standard elements before starting.
    • [ ] Launch Debugger; standard elements listed in the X++ output.
    • [ ] Breakpoints bound; variables, call stack and Infolog checked.
    • [ ] Disconnected promptly; environment responsive.
    • [ ] Next step decided: setup change, or a Chain of Command extension.
