    Scenario: Set Up ALM for a Team¶

    For a technical lead who starts a D365FO project with a team of developers in VS Code. At the end, the team has one Git repository on Azure DevOps with the model and project, every developer gets the code onto their own unified developer environment with one command, work items link to commits, reviews run before each pull request, and a pipeline (set up with Microsoft's tools) builds the deployable package.

    The situation¶

    Contoso starts a Finance implementation. Four developers, each with their own unified developer environment (UDE), will extend sales order processing (SalesTable, SalesFormLetter) and customer groups (CustGroup). Work items live in an Azure DevOps project FinOps. The lead has to set up:

    • a model ContosoExtensions (publisher Contoso, layer USR) referencing the standard application packages;
    • a repository ContosoFinOps in Azure Repos, with branch protection on main;
    • a project ContosoExtensions that every developer opens;
    • the team's naming rules for Copilot;
    • a build pipeline that produces the deployable package.

    What you need¶

    • A UDE for each developer, connected on their machine with Connect to Environment… (see Connect to Environment and Scenario: Set Up a New Developer Machine).
    • Git installed on every machine.
    • Azure DevOps project administrator rights (for the repository, policies and pipeline).
    • For the pipeline (general practice): the Dynamics 365 Finance and Operations Tools extension in the Azure DevOps organization and Microsoft's X++ build NuGet packages in an Azure Artifacts feed.

    Step by step¶

    Phase 1: Create the repository (Azure DevOps, general practice)¶

    1. In Azure DevOps, create the repository ContosoFinOps in project FinOps, initialized with a README so main exists.
    2. On main, add branch policies: minimum reviewers, Check for linked work items, and later a build validation with the pipeline from phase 6.
    3. Clone it on your machine, for example to C:\Repos\ContosoFinOps (VS Code's Git: Clone, or git clone).

    Phase 2: Create the model and the project (F&O Studio)¶

    1. Run Create Model… (Dynamics 365 view > Create). Enter ContosoExtensions, publisher Contoso, layer USR, and keep ApplicationPlatform, ApplicationFoundation and ApplicationSuite as referenced packages. Add other packages your extensions need. The model is created in its own package in the custom metadata folder. See Models, Packages and Versioning.
    2. Run Create D365FO Project…. Pick the model, keep the name ContosoExtensionsProject or change it, choose Browse… and pick C:\Repos\ContosoFinOps\Projects. F&O Studio writes Projects\ContosoExtensionsProject\ContosoExtensionsProject.rnrproj and a .slnx next to it. See D365FO Projects.

    Decision: one model or several? Start with one. Split into more packages only when parts must deploy separately or must not depend on each other; ask the F&O Architect agent if unsure (see below).

    Phase 3: Put the package into the repository and link it (F&O Studio)¶

    The package was created inside the custom metadata folder. Move it into the repository so Git tracks it, and link it back:

    1. Close VS Code, so nothing holds files of the package.
    2. Move the folder <custom metadata folder>\ContosoExtensions to C:\Repos\ContosoFinOps\Metadata\ContosoExtensions.
    3. Open VS Code and run Open Team Repository… > Use a Folder Already on This Machine… and pick C:\Repos\ContosoFinOps.
    4. F&O Studio finds the package by its Descriptor folder and lists it (checked). Confirm. It then:
    5. creates the junction <custom metadata folder>\ContosoExtensions -> C:\Repos\ContosoFinOps\Metadata\ContosoExtensions;
    6. writes .xpp\workspace.json with the package folder (Metadata/ContosoExtensions);
    7. refreshes the Application Explorer and builds the package;
    8. offers Deploy and Synchronize Database, and opens the repository's project.
    9. Check the summary message: "Linked 1 package(s) into ... ; all built."

    See Open Team Repository.

    Phase 4: Add the team files (F&O Studio and Git)¶

    1. Add a .gitignore at the repository root that keeps build output out (**/bin/, **/BuildLogs/, **/Resources/, **/Reports/, **/XppMetadata/, **/obj/, .vs/). The full list and reasons are in Source Control for X++.
    2. With the project open, run Create Team Rules for Copilot (Dynamics 365 view > Copilot). It creates .xpp\agent-rules.md in the first workspace folder (the project folder) with example rules. Replace the ABC examples with your rules, for example:
    ## Naming
- Prefix every new element with `Contoso`.
- Chain of Command classes: `<BaseObject>_Contoso_Extension`. Metadata extensions: `<BaseObject>.ContosoExtensions`.

## Code
- Every user-visible text is a label in the label file `ContosoLabels`.
- Batch work uses SysOperation (contract, service, controller); no RunBaseBatch.

    The MCP server adds this file to Copilot's instructions and restarts when it changes. See Team Rules. 3. Set xpp.git.baseBranch to main in your settings, and tell every developer to do the same. Change marks, Show Changed Elements and Review My Changes then cover the whole branch. See Git Changes in the Project View. 4. Commit everything on main (or through a first pull request if the policy already applies): Metadata\ContosoExtensions\..., Projects\..., .xpp\workspace.json, the project's .xpp\agent-rules.md and .gitignore. Push.

    Phase 5: Onboard each developer (F&O Studio)¶

    Each developer, on their own machine with their UDE connected:

    1. Runs Open Team Repository… > Clone a Repository…, enters https://dev.azure.com/contoso/FinOps/_git/ContosoFinOps and picks a parent folder. VS Code's Git extension clones it with the developer's sign-in.
    2. The packages listed in .xpp\workspace.json are offered, all checked. F&O Studio links them, builds them in dependency order and opens the project.
    3. Picks Deploy in the summary message (or runs Deploy Models to Environment later) so their UDE runs the code. See Deploy to Environment.
    4. Sets xpp.git.baseBranch to main.

    If a developer already has a folder with the package's name in their metadata folder, F&O Studio leaves it alone and says so; they remove or rename their folder and run the command again.

    Phase 6: Set up the pipeline (general practice)¶

    1. Publish Microsoft's X++ build NuGet packages (compiler and reference packages matching your application version) to an Azure Artifacts feed.
    2. Add packages.config and nuget.config to the repository.
    3. Create a pipeline that restores the packages, builds the solution or .rnrproj with MSBuild, and runs Create Deployable Package; publish the package as an artifact.
    4. Add the pipeline as build validation on main.
    5. In VS Code, Open Pipelines now opens https://dev.azure.com/contoso/FinOps/_build.

    F&O Studio does not create or run this pipeline. See Build Automation and Pipelines for the steps and Microsoft's documentation.

    Phase 7: Agree on the daily workflow¶

    Write the team's working agreement (in the README, for example):

    1. One branch per work item, feature/<id>-<name>, from main.
    2. Link Work Item… on every commit.
    3. Review My Changes against main before every pull request; paste the report into the pull request.
    4. Pre-Deploy Checklist and a deploy to your own UDE before asking for review.
    5. Sandbox and production deployments only from pipeline packages, through LCS or the Power Platform admin center.

    See Branching and Team Workflow and Scenario: From Work Item to Deployed Change.

    Doing it with Copilot¶

    Agent Use it for Example prompt
    F&O Architect The model and package split, dependencies, environment plan "We will extend sales order processing, customer groups and add two integrations. Propose models and packages and their references, and the environment plan."
    F&O Code Reviewer Checks that reviews follow the team rules in .xpp/agent-rules.md "Review this branch against main."
    F&O Release Manager Release checks, change summary, deployable package "Prepare ContosoExtensions for a sandbox release: run the checks and summarize the risk."

    Checkpoints:

    • The architect is read-only: it proposes, you create the models with Create Model….
    • The reviewer lists changes with xpp_diff_changes, which needs the models in Git; run it after phase 4.
    • The release manager asks before creating a package with xpp_package and never deploys to production.

    See Copilot Agents and Team Rules.

    Checklist¶

    • [ ] Repository created, main protected with reviewers, linked work items and build validation.
    • [ ] Model created with the right publisher, layer and referenced packages.
    • [ ] Project created inside the repository.
    • [ ] Package folder moved into the repository and linked with Open Team Repository….
    • [ ] .xpp\workspace.json, .xpp\agent-rules.md, .gitignore committed.
    • [ ] Every developer onboarded with Open Team Repository…, built and deployed to their UDE.
    • [ ] xpp.git.baseBranch set to main on every machine.
    • [ ] Pipeline builds main and publishes the deployable package.
    • [ ] Working agreement written down.
