    Scenario: Onboard to an existing codebase¶

    This walkthrough is for a developer who joins a team with an existing D365FO codebase, or a consultant who inherits a customer's custom models. At the end your machine has the team's packages linked and built, you know which models exist and how they depend on each other, where the code hooks into the standard application, what the team's rules are, and where the risky parts are. You can make your first change on day one.

    The situation¶

    You join a team that keeps its X++ code in an Azure DevOps repository:

    ContosoErp/
  .xpp/
    agent-rules.md        team rules for Copilot
    sod-rules.json        the team's segregation-of-duties rules
    workspace.json        the packages of the repository
  Metadata/
    ContosoCore/          package: shared tables, EDTs, labels
      Descriptor/
      ContosoCore/
    ContosoExtensions/    package: extensions of standard sales and customer processes
      Descriptor/
      ContosoExtensions/
  Projects/
    ContosoExtensions/ContosoExtensions.rnrproj

    ContosoExtensions references ContosoCore. Nobody wrote down what the extensions do; the people who built them left. Your first task will be a change to how sales orders are validated.

    What you need¶

    • A development environment set up for F&O Studio: a UDE connected with Connect to Environment…, or a cloud-hosted or VHD environment. See Scenario: Set Up a New Developer Machine.
    • Access to the repository (VS Code's Git signs you in when it clones).
    • The repository URL, for example https://dev.azure.com/contoso/erp/_git/ContosoErp.
    • Optional: GitHub Copilot for the F&O Code Archaeologist and F&O Architect agents.

    Step by step¶

    Phase 1: Get the team's packages on your machine¶

    1. Run Open Team Repository… (Dynamics 365 view > Model and project, or the command palette). It is a preview feature. See Open Team Repository.
    2. Choose Clone a Repository… and paste the URL (it must start with https:// or git@), then pick the folder to clone into. VS Code's Git extension clones it with its sign-in. If you cloned it already, choose Use a Folder Already on This Machine….
    3. F&O Studio finds the packages: the ones listed in .xpp/workspace.json, or else every folder (up to four levels deep) that has a Descriptor folder with model descriptors. Pick the packages to link; all are selected.
    4. Each package is linked into your custom metadata folder with a junction, the way teams set up Visual Studio. If a folder of that name already exists there and is not a link to this repository, it is left as it is and the summary says so.
    5. If the repository has no .xpp/workspace.json, F&O Studio writes one with the packages you picked. Commit it, so the next developer gets the same set.
    6. F&O Studio builds the packages in dependency order (here ContosoCore before ContosoExtensions; references to standard packages are already built). Progress shows per package; build errors go to Problems.
    7. The summary says how many packages were linked and whether all built, and offers Deploy and Synchronize Database (only Synchronize Database on cloud-hosted and VHD). On a UDE, deploy so the environment runs the team's code: Deploy runs Deploy Models to Environment; pick both packages and a Module sync. See Deploy to Environment.
    8. If the repository has projects (*.rnrproj), F&O Studio opens one (it asks which when there are several). Each project opens in its own workspace with its project and model folders. See D365FO Projects.

    Phase 2: Map the landscape¶

    1. In the Application Explorer, run Switch to Model View (Elements by Model). Models show by display name; expand ContosoCore and ContosoExtensions to see what each contains by type.

    1. Run View Model Dependencies… and pick ContosoExtensions. The diagram shows which models it references. A custom model that depends on many standard models touches many areas. See Models and Model Dependencies.

    1. Use Filter Application Explorer… with the team's prefix (Contoso) in the classic view to see every custom element grouped by type, next to the standard ones.
    2. Note the counts per type: many extensions and Chain of Command classes mean a model that changes standard behaviour; many tables and forms mean a model that adds its own module.

    Phase 3: Read the team's rules¶

    1. Open .xpp/agent-rules.md. It holds the team's naming, model, code, security and review rules, and Copilot follows it. If there is none, create it with Create Team Rules for Copilot and agree on it with the team. See Team Rules.
    2. If xpp.security.sodRulesFile points to .xpp/sod-rules.json, those are the team's segregation-of-duties rules; Check Segregation of Duties uses them instead of the built-in rules. See Segregation of Duties.
    3. Ask which branch pull requests go into and set xpp.git.baseBranch, so Review My Changes and the project view's Git marks compare with it. See Branching and Team Workflow.

    Phase 4: Find where the code hooks into standard¶

    Your first task is about sales order validation, so start there.

    1. Open SalesTable (Open Element…, Ctrl+Alt+O, type t:SalesTable) and go to validateWrite in the code view.
    2. The code lens above the method shows references, overrides, Chain of Command classes and handlers. Click it, or use Go to Implementations (Ctrl+F12), to list the team's wrappers and handlers next to Microsoft's. See Code Lens and Implementations and Chain of Command.
    3. Run Show Extensions and Handlers… on SalesTable for the full list: table extensions, Chain of Command classes, and event handlers on its form and data events (the cross-reference database doesn't record those; F&O Studio's own event handler index does).

    1. Open each wrapper of the team and read what it does before and after next.
    2. For the team's own classes, right-click and choose View Hierarchy (base and derived classes) and View References (who uses it). View Dependencies shows what an element uses. Each diagram exports Mermaid. See Hierarchy and Reference Diagrams.
    3. For custom tables, View Entity Relationship Diagram (ERD) shows the relations; choose the levels, direction and fields. See Entity Relationship Diagram.
    4. Find References on a custom element lists every user from the cross-reference database, with the calling code. See Find All References.

    Phase 5: Learn why the code is the way it is¶

    1. Right-click a custom element and choose View History. Pick a commit to see its code change; the commit message often names the work item. See Element History.
    2. If commit messages name work items (#123), Open Work Item… opens them in Azure Boards. See Azure DevOps and GitHub Integration.
    3. Compare Code… a team class with the standard class it was copied from, when you suspect a copy of standard code. See Compare Code and Metadata.

    Phase 6: Take a health check¶

    These reports show where the risk is, before you change anything.

    1. Upgrade Readiness on each team model (right-click the model in the Application Explorer): obsolete API uses, extensions that no longer match the installed application, collisions with other models. See Upgrade Readiness.
    2. Analyze Performance on the team's busiest classes. See Analyze Performance.
    3. Run Best Practice Checks on Project on the project you opened. See Best Practice Checks.
    4. Find Security Gaps on the team models, and the Security view's Your roles to see the team's roles and the standard roles they extend, with their license. See Security View.
    5. Find Unused Labels… on the team's label files, to see how tidy the model is. See Label Tools.
    6. Keep the reports: Export Report… in the Results view.

    Phase 7: Look at the data¶

    1. Right-click a custom table and choose Browse Table Data (database access needed; see Database Access). Use the company filter and the record inspector, which follows relations to the related rows. See Browse Table Data.
    2. Check which companies use the team's features and how much data there is. That tells you how careful a change must be.

    Phase 8: Make your first change¶

    1. Create a branch in the Source Control view.
    2. Make the change, Build Project (Ctrl+Shift+B), run the tests.
    3. Run Link Work Item… so the commit names the work item.
    4. Run Review My Changes before you open the pull request. See Scenario: Review a Pull Request.

    Doing it with Copilot¶

    Pick F&O Code Archaeologist in the agent picker. It explains legacy and unfamiliar custom code: what a model or element does, how it hooks into standard, dead code and leftovers from upgrades. It is read-only.

    Example prompts:

    • "Explain the model ContosoExtensions: what it adds, what it extends, and how it hooks into the sales order process. Draw the main flow."
    • "What do the team's wrappers of SalesTable.validateWrite check, and in which order do they run?"
    • "Find dead code in ContosoCore: elements and methods nothing references, obsolete calls, and copies of standard code that an extension point would replace."

    What it does:

    Step Tool
    Maps the model: object counts per type, then names per type xpp_list_model_objects
    Model details and dependencies xpp_get_model_info
    Follows the entry points (menu items, wrappers, handlers, batch jobs) and reads the code xpp_read_object
    Traces callers and users xpp_find_references
    Obsolete calls xpp_find_deprecations

    Its answer: what the model does in plain words, how it hooks into standard (entry points and wrappers), a Mermaid diagram of the main flow, risks, and clean-up candidates with evidence. The handoff Clean up switches to F&O Developer for the dead code it found (start a checkpoint first; see Scenario: Work Safely with Copilot).

    For the bigger picture, pick F&O Architect:

    • "Look at the models in this environment (ContosoCore, ContosoExtensions) and recommend whether the split and dependencies make sense. What would you change before the team grows?"

    It inspects the landscape with xpp_list_models and xpp_get_model_info and answers with options, trade-offs and a recommendation.

    For functional context, F&O Functional Explainer explains a form, field or process in business terms: "What does the field Credit review required on the customer form do, and which setup drives it?"

    Checklist¶

    • [ ] Environment set up; repository cloned and its packages linked with Open Team Repository….
    • [ ] .xpp/workspace.json in the repository (committed).
    • [ ] All packages built in dependency order; deployed (UDE) with a module sync.
    • [ ] Models and their dependencies understood (model view, View Model Dependencies…).
    • [ ] Team rules read (.xpp/agent-rules.md, SoD rules); xpp.git.baseBranch set.
    • [ ] Entry points into standard found for your first task (code lens, implementations, extensions and handlers).
    • [ ] Health check reports kept (upgrade readiness, performance, best practice, security).
    • [ ] First change on its own branch, linked to its work item, reviewed with Review My Changes.
