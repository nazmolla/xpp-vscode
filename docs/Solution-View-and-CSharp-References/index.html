    Solution View and C# References¶

    The D365FO Project view shows the whole solution around your X++ project, as Visual Studio's Solution Explorer does: the X++ project with its References, the other X++ projects of the solution, and the C# projects with their files. You can reference C# projects and .NET assemblies from X++, create a C# class library for your model, and build it. When you build or deploy the X++ project, F&O Studio builds the referenced C# projects first and copies their assemblies into your package, the same way Visual Studio's build does.

    When to use it¶

    • Your X++ code calls .NET code you own: a parser, an integration client, a calculation library.
    • You need a third-party .NET assembly in your package (a .dll with its dependencies).
    • C# code needs to call X++ classes and tables (Dynamics.AX.Application).
    • You want to edit the C# code next to the X++ code, with the C# extension's IntelliSense.

    Before you start¶

    • An open D365FO project (D365FO Projects). References belong to an X++ project and its model; without one you get Open a D365FO project first: references belong to an X++ project and its model.
    • MSBuild to build C# projects. F&O Studio uses, in this order: the xpp.build.msbuildPath setting; Visual Studio's or the Visual Studio Build Tools' MSBuild (found with vswhere); the .NET SDK's MSBuild (dotnet msbuild).
    • For C# editing, the C# extension for VS Code (optional; F&O Studio does not need it to build).

    The solution in the project view¶

    F&O Studio looks for a solution file (.slnx or .sln) that lists the open .rnrproj, in the project's folder and up to three folders above. If it finds one, the view shows:

    Node What it shows
    The open X++ project Its References node, then its elements by folder
    References Each C# project (C# project) and assembly (assembly) the X++ project references. A missing file has a warning icon and · not found. Clicking a C# project reference opens its .csproj. Empty: Add Reference… hint.
    Other X++ projects of the solution Collapsed, marked · not open, with their elements. Open This Project switches the window to that project.
    C# projects Every .csproj of the solution (C#) and every C# project the X++ project references but the solution does not list (C# · not in the solution), with their files

    The view's description is <solution> (solution).

    C# project files¶

    • SDK-style projects (<Project Sdk="...">) show every file under the project folder, like Solution Explorer. bin, obj, node_modules, packages, TestResults, hidden folders, .csproj/.user files and subfolders that contain a project of their own are left out. At most 3,000 files are listed.
    • Older projects show the items they list (Compile, Content, None, EmbeddedResource, Page, Resource...) and their Folder entries. Wildcard items and files outside the project folder are not shown.
    • Folders come first, then files, each sorted by name.
    • Click a file to open it. Files you add or delete in the project folders, and changes to the .csproj and the solution file, refresh the view on their own (build output in bin and obj is ignored).

    The C# project folders are also folders of the project's workspace (<Folder> (C#)), so the C# extension loads them.

    How to use it¶

    Add a reference¶

    1. Run Add Reference… from the References node (inline + or right-click), the open project node, the Project submenu of the view, or the Command Palette.
    2. The picker Add Reference to offers:
    3. Projects in the solution: C# projects of the solution that the X++ project does not reference yet;
    4. Browse for a C# Project…: any .csproj;
    5. Browse for an Assembly (.dll)…: any .NET assembly;
    6. New C# Project…: see below.
    7. For a C# project, F&O Studio first builds it (output in the X++ Build output channel), as Visual Studio does, so the reference names the assembly it produces. If the build fails you get .csproj did not build. See the X++ Build output.
    8. F&O Studio then:
    9. creates an AxReference element named after the assembly in the project's model (unless the model already has it). Through it, the X++ compiler resolves the assembly's types;
    10. adds a ProjectReference (C# project) or a Reference with a HintPath (assembly) to the .rnrproj;
    11. for a C# project, adds it to the solution if the solution does not list it, and adds its folder to the project's workspace.
    12. The message reads, for example, Added a reference to ContosoLibrary.csproj; model ContosoExtensions now has the reference ContosoLibrary. Build the X++ project to copy it into the package.

    F&O Studio refuses:

    • an assembly whose name starts with Dynamics.AX. (a compiled X++ package): add its model to your model's dependencies instead (Models and Model Dependencies);
    • a file that is not a .NET assembly;
    • a reference to a model other than the open project's model.

    Remove a reference¶

    1. Right-click a reference under References and choose Remove Reference (or run it from the Command Palette and pick the reference).
    2. Confirm: Remove the reference to ? The reference in model and the copy of .dll in its package go too. The C# project stays in the solution; an assembly file stays where it is.
    3. F&O Studio removes the .rnrproj item, the model's AxReference, and <assembly>.dll, .pdb and .xml from the package's bin folder, as Visual Studio does.

    Create a C# project¶

    New C# Project… creates a class library for your model, next to the X++ project, and references it.

    1. Run New C# Project… (References node, open project node, Project submenu, or Add Reference… > New C# Project…).
    2. New C# Project (1/3): name — default <Model>Library. It is also the assembly name and the root namespace; parts separated by dots are allowed (Contoso.Integration).
    3. (2/3): X++ packages the C# code uses — the packages your model depends on that have a compiled assembly. ApplicationPlatform, ApplicationFoundation and ApplicationSuite are preselected. Their assemblies are referenced, not copied. Your own package is not offered (it will reference this project).
    4. (3/3): parent folder — next to the solution (or next to the X++ project's folder), or Browse…. The project goes to <parent>\<name>.
    5. F&O Studio writes <name>.csproj and a sample class Greeter.cs, adds the project to the solution, opens Greeter.cs, builds the project and adds the reference.

    The generated project:

    <Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net48</TargetFramework>
    <RootNamespace>ContosoLibrary</RootNamespace>
    <AssemblyName>ContosoLibrary</AssemblyName>
    <DebugType>portable</DebugType>
    <PlatformTarget>AnyCPU</PlatformTarget>
    <FnOPackagesDirectory Condition="'$(FnOPackagesDirectory)' == ''">$([MSBuild]::GetRegistryValue('HKEY_CURRENT_USER\Software\Microsoft\Dynamics\AX7\Development\Configurations', 'FrameworkDirectory'))</FnOPackagesDirectory>
  </PropertyGroup>
  <ItemGroup>
    <Reference Include="Microsoft.Dynamics.AX.Xpp.AxShared">
      <HintPath>$(FnOPackagesDirectory)\bin\Microsoft.Dynamics.AX.Xpp.AxShared.dll</HintPath>
      <Private>false</Private>
    </Reference>
    <Reference Include="Microsoft.Dynamics.AX.Xpp.Support">...</Reference>
    <Reference Include="Dynamics.AX.ApplicationSuite">
      <HintPath>$(FnOPackagesDirectory)\ApplicationSuite\bin\Dynamics.AX.ApplicationSuite.dll</HintPath>
      <Private>false</Private>
    </Reference>
  </ItemGroup>
</Project>
    • .NET Framework 4.8, which the AOS runs.
    • Portable PDBs, which the VS Code debugger reads (Debugging C# Code).
    • Finance and Operations' assemblies are compiled against but never copied (Private false). Their folder comes from the registry value of the active configuration, so the project builds on every developer machine and follows the active version. A build pipeline can pass FnOPackagesDirectory instead.
    • X++ types are in the namespace Dynamics.AX.Application.

    The sample class shows how X++ calls it:

    namespace ContosoLibrary
{
    public static class Greeter
    {
        public static string Hello(string name)
        {
            return "Hello " + name;
        }
    }
}

    str greeting = ContosoLibrary.Greeter::Hello('world');

    Build a C# project¶

    Right-click a C# project node and choose Build C# Project. It runs MSBuild with -t:Build and -restore and shows the output in the X++ Build output channel. Open Project File (inline or right-click) opens the .csproj.

    Build the X++ project with its references¶

    You do not need to build the C# projects by hand before an X++ build. Build Project, Build Model (when the package being built is the open project's package), Deploy Models to Environment and the agent tool xpp_build run the reference step first, when the .rnrproj has references or items marked Copy to Output Directory:

    1. MSBuild runs on the .rnrproj itself. Visual Studio's build tasks need Visual Studio, so their import ($(BuildTasksDirectory)) is pointed at empty stand-in files, and a target that only resolves the references is added. This builds the referenced C# projects (with -restore).
    2. MSBuild reports the files to copy: the referenced assemblies with their dependencies, PDB and XML files and satellite assemblies (ReferenceCopyLocalPaths), and the files marked Copy to Output Directory (Copy always or Copy if newer).
    3. F&O Studio copies them into <package>\bin, keeping subfolders. Files marked Copy always are copied every time; the others when missing or newer.
    4. Files that are part of Finance and Operations (names starting with Dynamics.AX., or present in PackagesLocalDirectory\bin) are never copied: Not copied: … is part of Finance and Operations (reference it with Copy Local = False).
    5. Then xppc compiles X++. See Build Project and Model.

    Navigate between X++ and C¶

    Go to Definition works across the two languages: from X++ to the C# types and members of the referenced projects, and from C# to X++ elements in Dynamics.AX.Application. Hover and completion know the .NET types in X++. See Go to Definition.

    Options and settings¶

    Setting Default Effect
    xpp.build.msbuildPath empty MSBuild.exe used to build the C# projects and assemblies your X++ project references. Empty: Visual Studio's or the Build Tools' MSBuild, else the .NET SDK's

    How it works¶

    • Solution and C# project reading: src/solution.ts (no VS Code dependency). .slnx files are parsed for <Project Path="...">; .sln files for Project(...) = "...", "<path>" lines ending in a project extension. Solution folders are ignored.
    • Adding a project to a solution: .slnx files are edited directly (a <Project Path="..."/> line before </Solution>); .sln files with dotnet sln <solution> add <project>.
    • The view: ProjectTreeProvider in src/project.ts.
    • Commands Add Reference…, Remove Reference, New C# Project…, Build C# Project, Open This Project and Open Project File: src/references.ts.
    • The reference items and the AxReference element are written by the metadata server: bridge actions add_reference and remove_reference in MetaModelBridge.AssemblyReferences.cs, which call Microsoft's metadata API (CreateReference, DeleteReference) for the AxReference (name, assembly display name, version, public key token) and XppProject (server/Host/XppProject.cs) for the .rnrproj. Paths in the .rnrproj are relative to the project folder (absolute when on another drive). A project reference also carries the C# project's GUID when it has one.
    • The reference step of the build: src/dotnetReferences.ts for the extension's build and deploy, and server/Host/ProjectReferences.cs for xpp_build. Both implement the same rules. MSBuild is called with -t:XppStudioResolveReferences -getItem:ReferenceCopyLocalPaths -getItem:AllItemsFullPathWithTargetPath -getResultOutputFile:<json>; the stand-ins and the extra target are written to %TEMP%\xpp-vscode-msbuild only when their content changes, so referenced projects are not rebuilt for nothing.

    Limitations¶

    • C# editing, IntelliSense and refactoring come from the C# extension, not F&O Studio.
    • F&O Studio does not create test projects, NuGet packages or other project types; New C# Project… creates a class library.
    • .sln editing needs the .NET SDK (dotnet sln). .slnx files are edited without it.
    • References are kept per X++ project. The reference step runs for the open project's package only; other packages you build or deploy at the same time get no C# files copied.
    • Hitting a breakpoint in referenced C# code on a UDE or VHD is not tested yet (release notes of 0.16.0); see Debugging C# Code.

    Symptom Cause Fix

    .csproj did not build. See the X++ Build output. The C# project has compile errors, or MSBuild could not restore Read the X++ Build output and fix the C# project
    Build .csproj first: its assembly was not found. The build produced no assembly Build the project; check its output path
    … is a compiled X++ package: add its model to your model's dependencies instead. You picked a Dynamics.AX.* assembly Add the package with Update Model Parameters…
    … is not a .NET assembly. Native DLL Reference the .NET wrapper; copy native files with Copy to Output Directory in a C# project
    Building the references failed. MSBuild came from the .NET SDK … No Visual Studio or Build Tools MSBuild found Set xpp.build.msbuildPath, or install the Visual Studio Build Tools
    Not copied: … is part of Finance and Operations A referenced file is a Finance and Operations assembly Set Copy Local (Private) to false on that reference
    A reference shows · not found The .csproj or HintPath file moved Remove the reference and add it again
    … was not added to : … in the output dotnet sln add failed for a .sln Add the project to the solution yourself
