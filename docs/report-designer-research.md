# Report designer and scan-to-report agent: research

Research for two related features:

1. A **precision design (SSRS/RDL) designer** in F&O Studio, the last major Visual Studio-only piece. It must render
   accurately enough for cheques, purchase orders and invoices on preprinted stationery.
2. A **scan-to-report agent**: given a scanned report (preprinted or not), build the whole report chain (data source,
   contract, dialog, controller, report, menu item, security, print management) and, for preprinted forms, place every
   field at the measured position.

Sources are marked: **[Code]** decompiled or read from the installed D365FO tools and PackagesLocalDirectory (10.0.2790.108),
**[Test]** run on this machine, **[Learn]** fetched from Microsoft Learn (quoted), **[Unverified]** not yet confirmed.

## 1. Answer in short

- Nothing technical blocks it. Visual Studio does not have its own designer: F&O's tools generate a temporary `.rdlc`
  file and open it in the separate Marketplace extension **Microsoft RDLC Report Designer**, then copy the saved RDL back
  into the design's `Text` property **[Code]**. That designer is closed, WinForms and Visual Studio-only, so we write our
  own editor; the data it edits is plain RDL XML in one metadata property.
- **Rendering can be exact**: Microsoft's own SSRS processing and rendering engine (the Report Viewer runtime,
  `LocalReport`) renders a compiled D365FO precision design to PDF/PNG headless, in about 1 s, with no report server
  **[Test]**. The preview can use the real engine instead of an approximation. Visual Studio has **no local preview at
  all** **[Code]**, so this is better than Visual Studio.
- `reportsc.exe` (in `PackagesLocalDirectory\bin`) compiles precision and auto designs into the deployable RDL without
  Visual Studio, also for custom packages **[Test]**. F&O Studio's build does not run it yet (see §10).
- The hard parts are a tablix editor (99% of standard designs use one) and keeping RDL intact on save (four schema
  versions, unknown elements, D365FO custom properties).

## 2. How Visual Studio does it [Code]

Decompiled from `Microsoft.Dynamics.Framework.Tools.Reports.DesignTime.17.0.dll`, `…Reports.Build.dll` and the add-ins in
the FinOps tools folder.

| Step | Visual Studio |
|---|---|
| Open | `Design.Initialize` writes `<Report>.<Design>.rdlc` to a temp folder, generated by `ReportGenerator.GenerateRdlForDesign` in **Designer** mode; `DTE.OpenFile` opens it in the RDLC Report Designer extension (offered from the Marketplace when missing). Other edits to `Text` are blocked while it is open. |
| Save | On `DocumentSaved`, `PrecisionDesignImporter.ImportDesign` copies `<EmbeddedImages>` into `AxReport.EmbeddedImages` and sets `AxReportPrecisionDesign.Text = xml.InnerXml`. |
| New precision design | Generated from an auto design (Designer mode), then imported. |
| Datasets | Restore/refresh (`ReportDataSet.Restore`, `DataSetQueryChangeRule`) rebuilds fields and parameters from metadata. Strategies: **RDP** (`SELECT * FROM <RdpClass>.<TmpTable>`, field aliases `Tmp.1.Field`), **Query** (AOT query), **Enum provider** (`Name`, `Value`, `Label`). SQL and BusinessLogic datasets throw "not supported". |
| Parameters | From the RDP contract (`SRSReportParameterAttribute` → `[DataMember]` parm methods; `SysOperationLabel` = prompt; `AifCollectionType` = multi-value; nested contracts flattened), plus `AX_RdpPreProcessedId`, `ReportProviderDynamicFilter` (provider with a query), and framework parameters `AX_PartitionKey`, `AX_CompanyName`, `AX_UserContext`, `AX_RenderingCulture`, `AX_ReportContext`. |
| RDL regeneration | `MultiElementExportDecorator` (every mode) replaces `<DataSources>` (`AutoGen__…`, `DataProvider` = `AXREPORTDATAPROVIDER`/`AXQUERY`/`AXENUMDATAPROVIDER`/…), `<DataSets>`, `<ReportParameters>`, `<EmbeddedImages>` and `<CodeModules>`. `ReportParametersLayout` is never generated (kept as is). So a designer only edits layout; data elements are regenerated from metadata. |
| Add-ins | PrecisionDesignTools: "Add placeholders" / "Update all placeholders" (sets `TextRun/Label` from `Value`). ReportingSandboxRules: menu that writes `RDLSandboxing` into a local SSRS `rsreportserver.config` (allowed types listed in §5.4). |
| Preview | None. "Deploy reports" pushes to a local SSRS (one-box only). |

**reportsc / build pipeline** (`PrecisionDesignReportGenerator`, Server mode), decorators in order: remove custom
properties except `AXDataType`; regenerate data elements; drill-through parameters; dynamic parameter properties;
`Labels!@SYS123` → string literal `"Labels!@SYS123"` (**labels are resolved at run time**, not compile time); re-parse
expressions and wrap business-logic calls in `DataMethodUtility.PostDataMethodEvaluation(UpdateAxContextPartition(…), …)`;
EDT format properties (`AXEDTFormat`, `AXEDTTextAlign`, …); `AXDisableRuntimeTransformation(Groups)`; `AXFieldName`
for drill-through. The namespace is **not** upgraded (Cheque_US stays 2010/01).

**At run time** the AOS transforms the RDL before rendering (skipped per group by `DisableRuntimeTransformation` /
`DisableIndividualTransformation`): EDT format and layout, RDL language, **font replacement**, drill-through, **label
resolution**, hyperlinks, tablix page name (also upgrades 2008 → 2010), **right-to-left flipping**, subreports/AutoFix.
A faithful preview must apply label resolution and EDT formatting the same way.

**Deployment on a UDE** (from the AOS code, untested): the AOS reads `<package>\Reports\<Report>.<Design>.rdl`, transforms
it and pushes it to the reporting service when the report runs. So `reportsc` output in the package's `Reports` folder
travels with the normal package deployment.

`reportsc` usage **[Test]**: `-metadata=<root with all packages> -modelmodule=<model> -name=<report> -output=<pkg>\Reports
-log=… -xmllog=…`. 2–3 s per report. `-metadata` takes one root, so for a custom package use a folder of junctions to
every standard package plus the custom one (`RuntimeSymLinks\<org>` has only 3 junctions and does not work). Without
`-name` it deletes every `*.rdl` in the output folder first.

### 3.1 How Microsoft builds a preprinted cheque (Cheque_US) [Code]

One dataset (`Cheque_USDS`, RDP `ChequeDP.ChequeTmp`). The body is a single tablix (one row per cheque, page break per
cheque) with three rectangles: slip above, cheque, slip below. **The cheque's vertical position (top/middle/bottom from
Bank cheque layout) is produced by text**: `CanGrow` textboxes in Courier New hold `ChequeTopDrop` (blank lines) and the
monospace `SlipTxt`, and their growth pushes the cheque rectangle down. Fields inside the cheque rectangle are absolute
(company, date, amount box, amount in words, signatures as images, MICR line in `IDAutomationMICR` 12 pt at 3 in from the
top of the rectangle). So a correct preview must reproduce **grow-and-push** and monospace line heights, not just
absolute coordinates. Related code: `ChequeController` (`getChequeReport`, `determineReportMenuOutput`, delegate
`initChequeReportFromChequeFormTypeDelegate`), `ChequeDP` (`populateChequeTmp`, `insertChequeTmp`, MICR from
`displayMICRLine()`, amounts in words via `numerals2LetterPart1/2`), `ChequeTmp` (TempDB), `BankChequeLayout`
(`ChequeStartPosition`, `ChequeSlipCopies`, `TopMargin`, `BottomMargin`, `Micr*`, `Signature*`).

## 4. RDL and rendering rules the designer and preview must follow

### 4.1 Verified rules

- Sizes: `RdlSize` = number + one of `pt`, `pc`, `in`, `mm`, `cm`; no negative values unless allowed; missing = 0 **[Learn]**
  ([MS-RDL RdlSize](https://learn.microsoft.com/en-us/openspecs/sql_server_protocols/ms-rdl/b40c092e-4fe5-4f7b-a0bf-c98df1361c90)).
  Keep each value in the unit it was written in; standard designs mix `in` and `pt`.
- Textbox `CanGrow`, `CanShrink`, `KeepTogether`: missing means **false** **[Learn]** (MS-RDL). Padding applies only to
  Textbox, Subtotal and Image and is at most 1000 pt; its default is not stated in MS-RDL **[Unverified]**.
- Page width: "check that the width of the report body, including margins, is not larger than the physical page size
  width"; the body grows past the page edge → horizontal/vertical page breaks; items in the margin are clipped; margins
  apply only to hard-page renderers (PDF, image, print) **[Learn]**
  ([Pagination](https://learn.microsoft.com/en-us/sql/reporting-services/report-design/pagination-in-reporting-services-report-builder-and-ssrs)).
- Growth: "Renderers maintain the minimum space between report items that you define in the report layout… the distance
  between the report items becomes the minimum distance that must be maintained as the report grows" **[Learn]**
  ([Rendering behaviors](https://learn.microsoft.com/en-us/sql/reporting-services/report-design/rendering-behaviors-report-builder-and-ssrs)).
- **Overlapping items are supported in hard page-break formats, including print, but not in HTML, Word, Excel, Preview or
  the Report Viewer control** (they are moved there) **[Learn]**
  ([Rendering report items](https://learn.microsoft.com/en-us/sql/reporting-services/report-design/rendering-report-items-report-builder-and-ssrs)).
  So the preview must use the PDF/image renderer, never the interactive one.
- Always-hidden items keep their space; items hidden by an expression let items below/right move up **[Learn]**.
- PDF/image: page header and footer never grow; overflowing content is clipped; their height is reserved even where
  hidden; an item that cannot be kept together is clipped at the page boundary and continues on the next page **[Learn]**.
- Global collections in page header/footer: Fields and ReportItems allowed, at most one report item reference per
  expression; `PageNumber`/`TotalPages` only in header/footer **[Learn]**
  ([MS-RDL restrictions](https://learn.microsoft.com/en-us/openspecs/sql_server_protocols/ms-rdl/ab498655-85ee-454a-bb71-ef3f7c017f65)).
- PDF fonts: subsets of TrueType fonts are embedded when the font allows it; fonts must be installed where the report
  renders; a missing font gives wrong glyph mappings **[Learn]**
  ([Export to PDF](https://learn.microsoft.com/en-us/sql/reporting-services/report-builder/exporting-to-a-pdf-file-report-builder-and-ssrs)).

### 4.2 Fonts in D365FO (critical for cheques)

"The service doesn't support installing custom fonts in customer environments" **[Learn]**
([Supported fonts](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/supported-fonts)). The
page lists about 273 available fonts, among them **`MICR E13B 2.1`, `IDAutomationMICR`, `OCRB`, `OCR A Extended`**, the
`BC C128`/`C39` barcode families, Courier New, Segoe UI, Tahoma, Arial, Calibri and CJK fonts. The designer should offer
only this list (warn on anything else), and the preview must warn when a font used by the design is not installed on the
developer's machine (the MICR fonts usually are not, so the preview substitutes them; the spike showed exactly that).

## 5. Rendering engine for the preview

### 5.1 Spike [Test]

`Microsoft.ReportingServices.ReportViewerControl.Winforms` 150.1652.0 (NuGet, net40) + `Microsoft.SqlServer.Types`, a
40-line .NET Framework console program: load `Cheque_US.Report.rdl` from `reportsc`, drop `<CodeModules>`, replace the two
`Microsoft.Dynamics…` expressions by a literal, give each dataset a one-row `DataTable` (columns = `DataField` aliases with
the `rd:TypeName` types) and every parameter a dummy value, then `LocalReport.Render("PDF")` and `Render("IMAGE")` (PNG,
150 dpi). Result: correct page, 1 s, slip text pushing the cheque down as designed; warnings only for the stubbed
watermark image and a `Transparent` section background. Labels showed as `Labels!@SYS…` (expected, resolved at run time)
and the MICR line used a substitute font (not installed here).

### 5.2 What the preview service has to add

- **Labels**: replace the `"Labels!@…"` literals with text from `LabelStore` for the chosen language.
- **D365FO functions**: the business-logic calls need an AOS session (`UpdateAxContextPartition`). Rewrite
  `PostDataMethodEvaluation(ctx, x)` → `x` and map the common functions (`ToDisplayStringAmount`, `ToDisplayStringDate`,
  `ConvertUtcToAxUserTimeZoneForUser`, `GetFullCompanyNameForUser`, `NumeralsToTxt`, `SplitReportItem`,
  `GetExtendedDataTypeFormat`, …) to a small local shim module; anything else renders as a marked placeholder.
- **EDT formatting** (`AXEDTFormat` custom properties) and right-to-left flipping, as the AOS transform does.
- **Data**: sample rows generated from the dataset fields, editable in the preview, or real rows: for a TempDB RDP the
  rows exist only during the report run, so real data needs the report to run on the environment (later).
- **Item map**: alongside the PNG, return every item's rendered box in mm (from the RDL plus growth), so the designer
  and the agent can measure.

### 5.3 Licence [Learn, Unverified legally]

The Report Viewer runtime licence (`License_ReportViewer.rtf`, linked from the NuGet package) allows distributing the
object code "in programs you develop" if the program adds significant functionality, end users accept terms at least as
protective, the program shows its copyright notice and the distributor indemnifies Microsoft; Windows only; no
commercial hosting. Recommendation, in line with this repo's rule of not shipping Microsoft binaries: **download the
package from nuget.org on first use** after the user accepts the licence, like the FinOps tools download. Have the terms

### 5.4 Sandbox rules (what expressions may call) [Code]

D365FO's `RdlSandboxing.xml`: max expression length 27,000; allowed types: BusinessLogic `ColorUtilities`,
`ConversionUtilities`, `CustomServiceProvider`, `DataProvider`, `DrillThroughProvider`, `FormattingUtilities`,

`Convert`, `TimeSpan`, …; `Microsoft.VisualBasic` `Strings`, `Conversion`, `DateAndTime`, `Interaction`, …; about 150

## 7. Report chain and data sources

### 7.1 Chain elements [Code]

Verified names in 10.0.2790.108:

- Contract: `DataContractAttribute`, `DataMemberAttribute`, `SysOperationLabelAttribute`, `SysOperationHelpTextAttribute`,
  `SysOperationDisplayOrderAttribute`, `SysOperationGroupAttribute`, `SysOperationGroupMemberAttribute`,
  `SysOperationContractProcessingAttribute` (UI builder), `SysOperationValidatable`.
- UI builder `SrsReportDataContractUIBuilder`; controller `SrsReportRunController` (`parmReportName(ssrsReportStr(R, D))`,
  `parmShowDialog`, `startOperation`); print settings `SRSPrintDestinationSettings`. Microsoft's doc comments:
  `prePromptModifyContract` runs before the dialog and **not in batch**; `preRunModifyContract` runs before the report
  (query changes and hidden contract values belong here so they also apply in batch) **[Learn, quoted in a community
  thread]**.
- Print management: `PrintMgmtDocType` delegates `getDefaultReportFormatDelegate`, `getQueryTableIdDelegate`,
  `getQueryRangeFieldsDelegate`, `getPartyTypeDelegate`, `getEmailAddressDelegate`, `getDestinationPartyTypeAndIdDelegate`,
  `getPartyRecIdDelegate`; `PrintMgmtReportFormatPopulator` protected `addDocuments`, `addStandard`, `addOther`,
  `addNonSSRS`.

Artifacts of a new report (build order): labels → temporary table(s) → query (optional) → contract → UI builder
(optional) → data provider → controller → AxReport (datasets restored, design) → output menu item → privilege (and
duty/role) → menu entry → print management hookup (business documents) → build, `reportsc`, deploy, run. The report
wizard (`src/scaffolding/report.ts`) already builds most of this chain with an auto design; the agent extends it.

### 7.2 Dataset data source types

The metadata enum `DataSourceType` has five values (`Query`, `ReportDataProvider`, `EnumProvider`, `BusinessLogic`,
`DatabaseStoredProcedure`), but the D365FO tools support three (`DataSetStrategyFactory` **[Code]**); the others throw
"not supported" and must not be generated. Standard datasets: ReportDataProvider 1,023, Query 289 (the default, not
written in the XML), EnumProvider 51. Standard data providers: `SrsReportDataProviderBase` 367,
`SrsReportDataProviderPreProcessTempDB` 331, `SrsReportDataProviderPreProcess` 38 (direct subclasses); 447 also carry
`SRSReportQueryAttribute` **[Code]**.

| Type | Use when | How |
|---|---|---|
| **Query** | The data is a selection/join of tables with no X++ calculation; users filter with the query dialog. "A query should be considered before you use a Report Data Provider class"; "Filtering occurs in SQL which is faster. There are no X++ classes to develop." **[Learn, AX 2012 guidance]** | Dataset `Query` = `SELECT <Table>.1.<Field>,… FROM <AOT query>` (for example `QMSDispensingTicket`), `DynamicFilters` = the user's range dialog; fields with `Dynamic = No` on the query's data sources limit the columns. Display methods are allowed but run per row: avoid on large sets. Microsoft's D365 example of a query report with a UI builder: `FMCustomerList` **[Learn]**. |
| **Report data provider (RDP)** | The data needs X++: calculations, aggregation, calling business classes, logic that depends on a dialog parameter, data from several sources combined into rows, or more filters added at run time **[Learn, AX 2012 guidance]**. | Dataset `Query` = `SELECT * FROM <DP class>.<Tmp table>`. Class with `[SRSReportParameterAttribute(classStr(Contract))]` (fixed parameters) and/or `[SRSReportQueryAttribute(queryStr(Query))]` (the user's ranges, read with `this.parmQuery()` and run with `QueryRun`, never plain selects), `processReport()` filling the temporary table(s), one `[SRSReportDataSetAttribute(tableStr(Tmp))]` getter per dataset (one RDP can return several datasets: `SalesInvoiceDP` returns 7) **[Code]**. |
| **Enum provider** | A report parameter that is an enum and should show as a drop-down of enum values. | Dataset with `DataSourceType` EnumProvider and `Query` = the enum name (for example `EventTypeTrigger` in `AlertsetupReport`); fields `Name`, `Value`, `Label` **[Code]**; reference it from the parameter's valid values. |

### 7.3 Which RDP base class and table type [Code, Learn]

Read from the framework classes in ApplicationFoundation and from the standard business documents:

| Base class | Tables | Use for | Standard examples |
|---|---|---|---|
| `SrsReportDataProviderBase` | TempDB (InMemory works only for small sets, about 1,000 rows **[Learn, AX 2012]**) | Ordinary reports. Data is produced while SSRS waits: the interactive limit is **10 minutes** ("Service time-outs in deployments are fixed and limit interactive connections to 10 minutes") **[Learn]**. | Most list reports |
| `SrsReportDataProviderPreProcessTempDB` | TempDB with `CreatedTransactionId` = Yes | Long-running reports; data is produced **before** SSRS is called. Microsoft's doc comment: "This is the preferred approach to enable pre-processing of reports." Call `setConnection(this.parmUserConnection())` on every table instance (or `takeOwnershipOfTempTable`, which does it) **[Code]**. Needs a controller, and the output menu item must point at the controller, not the report **[Learn]**. For large volumes opt in to `parmSkipReportTransaction` (PU55+) and manage transactions on the user connection (`this.parmUserConnection().ttsBegin()`) **[Learn]**. | `ChequeDP`, `CustAccountStatementExtDP` |
| `SrsReportDataProviderPreProcess` | **Regular** tables named `*Tmp`, `CreatedTransactionId` = Yes | Pre-processing with regular tables. Microsoft's comment: "It is critical that any inserts to tables uses the UserConnection that is provided in `parmUserConnection`" **[Code]**. Changes to these tables need a **database sync**. For new reports prefer the TempDB variant. | `SalesInvoiceDP` (via `SalesInvoiceDPBase`), `PurchPurchaseOrderDP`, `SalesConfirmDP` |

Pre-processing does not make a report faster; it avoids the time-out (Martin Dráb on the community forum). Microsoft's
migration steps for a report that times out: base class → `SrsReportDataProviderPreProcessTempDB`, table InMemory →
TempDB, rebuild, **Restore** the dataset, redeploy, add a controller, point the output menu item at it **[Learn]**
([Prevent long-running reports from timing out](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/prevent-long-running-reports-timing-out)).
Company-specific data: the temporary table needs `SaveDataPerCompany` = Yes **[Learn, AX 2012]**. Fill tables set-based
where possible (`insert_recordset`); a data event handler on the table silently downgrades set-based inserts to row by
row **[Learn]** ([Skip report transaction](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/skip-report-transaction-tempdb-preprocessing)).

## 8. New report vs extending a standard report

D365FO has no report extension element: a standard report's design and datasets cannot be changed in place **[Code,
Learn]**. "Customizations to reporting solutions in the standard application are fully supported using a pure extension
model"; standard designs stay available, and "the platform supports run-time selection of the target report" **[Learn]**
([Customize App Suite reports using extensions](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/customize-app-suite-reports-with-extensions)).
So "extending" a report means: keep Microsoft's data provider, contract and controller logic, extend what can be extended
(temporary table, data provider methods, contract, menu item, print management), and **duplicate only the report
(design)** into the custom model.

### 8.1 Decision tree

| Need | Approach |
|---|---|
| A report that has no standard counterpart | **New report** (§7). |
| Another layout of a standard business document (invoice, PO, confirmation, packing slip, cheque…) on the same data | Duplicate the report ("Duplicate in project"), rename (`SalesConfirmExt`), change the design; register it for print management (§8.3); the user picks it in Form setup > Print management (settings are per legal entity) **[Learn]** ([Custom designs for business documents](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/custom-designs-business-docs)). |
| Another layout of a standard non-document report (list, statement) | Duplicate the report; redirect with a post-handler on the controller's `construct` that calls `parmReportName(ssrsReportStr(NewReport, Report))`, or extend the output menu item and point it at your controller or report **[Learn]** ([Extend report menu items](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/extend-report-menu-items)). |
| Extra fields on a standard report | Table extension on the temporary table; fill the fields from a hook (§8.2); duplicate the report and **Restore** its dataset so the new fields appear; route as above **[Learn]** ([Expand App Suite report data sets](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/expand-app-suite-report-data-sets)). If the table is a regular `*Tmp` table (`SrsReportDataProviderPreProcess` reports), sync the database. |
| Extra dialog parameters | Extension class of the contract with new `[DataMemberAttribute]` parm methods (supported since Platform update 23; defaults through a field initializer, because an extension cannot add `SysOperationInitializable`) **[Community, ER-Consult 2019]**; read them in the data provider hook; duplicate the report and Restore the dataset so the parameter is added. Whether an SSRS contract extension always shows in the dialog: **[Unverified]**, test it. |
| A whole new dataset on a standard report | Learn names "Composing custom datasets: extending an existing RDP class to return a custom dataset" but has no article **[Learn]**; practical route: a separate RDP for the extra dataset in the duplicated report, or extra fields on an existing temporary table. **[Unverified]** |
| Business users own the layout (Word/Excel), no deployment | Electronic Reporting / Business document management, for the documents in Microsoft's list (sales invoice, free text invoice, project invoice, purchase order, sales confirmation, picking list, quotation, statement, collection letter…) **[Learn]** ([Business document management](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/analytics/er-business-document-management)). Pixel-exact preprinted layouts (cheques) stay SSRS. |

|---|---|---|
| Chain of Command on the data provider (`[ExtensionOf(classStr(SalesInvoiceDP))]`) | Preferred when a suitable method is wrappable. Business document DPs expose protected `populate…`/`insertInto…`/`init…` methods (`SalesInvoiceDP.populateSalesInvoiceTmp`, `insertIntoSalesInvoiceTmp`, `populateSalesInvoiceHeaderFooterTmp`, …) **[Code]**. Methods marked `[Hookable(false)]` or `[Wrappable(false)]` cannot be used. |
| Post-handler on `processReport` | Once, after all data is produced: update the rows (`while select forUpdate … update()`) **[Learn]**. | With pre-processed reports use the user connection (§7.3). |

### 8.3 Print management registration [Code, Learn]

- Default design for a document type: subscribe to `PrintMgmtDocType.getDefaultReportFormatDelegate` and return
  `ssrsReportStr(MyReport, Report)` for the `PrintMgmtDocumentType`; check that no earlier subscriber already set a
  result. Microsoft's own: `QMSPrintMgmtDelegatesHandler` (AdvancedQualityManagement), `RentalPrintMgmtDelegatesHandler`
  (RentalManagement).
- Make the design selectable in the Report format list: CoC on `PrintMgmtReportFormatPopulator.addDocuments` that calls
  `next addDocuments()` and `this.addOther(docType, ssrsReportStr(R, Report), ssrsReportStr(R, Report),
  #NoCountryRegionId)` (or `addStandard`). Microsoft's own: `PrintMgmtReportFormatPopulator_Kitting_Extension`,
  `QMSPrintMgmtReportFormatPopulator_Extension`. The formats are stored in `PrintMgmtReportFormat`.
- Learn's business document sample also adds a controller subclass whose `main` calls
  `initArgs(_args, ssrsReportStr(SalesConfirmExt, Report))` and keeps the standard `renderingCompleted` subscription for
  journal printing, plus a menu item extension pointing at that controller.

### 8.4 Pitfalls

- New temporary table fields missing in the design: the duplicated report's dataset was not restored **[Learn]**.
- Changes not visible after deploying: rebuild, deploy the report, sync the database, clear caches **[Community]**.
- Report not in the print management list: the populator extension or delegate is not built/deployed, or the format was
  not selected in Form setup **[Community]**.
- A duplicated report does not receive Microsoft's later design fixes; data provider logic keeps receiving them, which is
  why the data stays with the standard DP. After each update, compare the duplicate with the new standard design (F&O
  Studio's Compare can do this).
- Pre-processed reports run from the menu item directly skip pre-processing: the menu item must point at the controller
  **[Learn]**.

## 9. Scan-to-report agent

### 9.1 How practitioners do it

From Microsoft's preprinted-stock guidance and practitioner write-ups ([AX 1099 preprinted stock blog](https://community.dynamics.com/blogs/post/?postid=95780a97-ede2-4fee-a41a-dac73b83b911),
[Docentric cheque design](https://ax.docentric.com/designing-checks-as-easy-as-it-gets-in-d365fo/)):

1. Measure the real form: paper size, margins, offsets of each field, MICR line position, stub offsets.
2. Put a scan of the blank form behind the design at natural size (`BackgroundImage`) while designing; remove it before
   release.
3. Use fixed-position textboxes (`CanGrow`/`CanShrink` false, padding 0) grouped in fixed rectangles; fixed-height rows
   for line items; monospace fonts for column-aligned slip text.
4. Print on plain paper, hold it over the form against the light, nudge Left/Top, repeat. Drift between printers and
   stock batches is normal; keep a calibration offset.
5. Print at actual size (never "fit to page"); mind the printer's unprintable margin; Letter vs A4 mismatches give an
   offset that grows down the page.

### 9.2 Agent design

A new persona, **F&O Report Builder** (defined in `scripts/agent-definitions.js`), with the knowledge in §3.1, §4, §7,
§8 and §9.1, and these tools (new, server side unless noted):

| Tool | Purpose |
|---|---|
| `xpp_measure_image` | Load a scan or PDF page; calibrate (paper size, or two points with a known distance → px/mm, checked in x and y); deskew; detect horizontal/vertical rules and boxes; OCR words with boxes (Windows OCR, local, no cloud); return everything in mm from the page's top-left. Also returns the image with a mm grid and rulers drawn on it, so the model's vision can read positions. |
| `xpp_render_report` | Build the design (`reportsc`), render it with sample or given data through the real engine; return page PNGs and the item map in mm. |
| `xpp_compare_layout` | Overlay the rendered page on the calibrated scan (difference image) and list each mapped field's offset in mm. The agent iterates until every field is within tolerance (for example 0.5 mm). |
| Existing tools | `xpp_create_object`, `xpp_update_object`, `xpp_build`, labels, security, `xpp_find_examples` (standard reports such as `Cheque_US`, `PurchPurchaseOrder`, `SalesInvoice`). |

Procedure the agent follows:

1. Ask for the facts it cannot see: preprinted or not, paper size, which document (new report, or a new design for a
   standard business document through print management), which fields map to which data, the target model.
2. Measure the scan; list every field with position, size, font size (from glyph height), alignment, and repeating
   regions (line items: rows per page, row height).
3. Decide new vs extend with the decision tree in §8.1, after checking for a standard counterpart (`xpp_find_examples`,
   print management document types). Extend: duplicate the standard report, extend the temporary table, fill fields
   through the hook that fits the data provider (§8.2), register through print management (§8.3). New: pick the data
   source type and base class from §7.2/§7.3 (Query when no X++ is needed, RDP otherwise, PreProcessTempDB when it can
   run long, Enum provider for enum parameters), then contract (+ UI builder for lookups) and controller.
4. Generate the precision design: explicit page size and margins, body width + margins ≤ page width, fixed fields as
   absolute textboxes, a fixed-height tablix for lines with a fixed number of rows per page and continuation pages
   (totals on the last page), fonts from the D365FO list, the scan as a design-time overlay only.
5. Build, render, compare, adjust; repeat until within tolerance. Report the remaining risks: fonts not installed
   locally (MICR), printer offsets, the plain-paper test.
6. Menu item, privilege, print management registration, labels; build and deploy.

## 10. Gap found in F&O Studio

F&O Studio's build (`xpp_build`, Build command) does not run `reportsc`, so a report created or changed in F&O Studio
(including the report wizard's) gets no `<package>\Reports\*.rdl`, which the AOS reads at run time. Add a report step to
the build (only for reports in the project/model, with the junction metadata root from §2), and verify on a UDE that a
deployed custom report runs.

## 11. Proposed phases

1. **Report build step**: `reportsc` in the build (§10). Verify a wizard report end to end on a UDE.
2. **Real-engine preview**: server render service (Report Viewer downloaded on first use), labels, function shims,
