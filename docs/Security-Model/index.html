    Security Model¶

    F&O Studio runs local programs (the X++ compiler, a metadata server, the debugger proxy), signs in to your Dynamics 365 environments, and lets Copilot read and change metadata. This page explains what it is allowed to do, what it refuses, and how those rules are enforced and tested.

    In short: only your own models are writable, the server enforces that for every write, Copilot works inside the scope you set, business data never reaches Copilot's server process, credentials stay in VS Code's secret storage, and no Microsoft assemblies or data leave your machine through F&O Studio.

    Principles¶

    Rule Where it is enforced
    Standard models and their elements are never changed Bridge dispatcher, centrally for every write action (IWritePolicy)
    Metadata changes go through Microsoft's metadata API, not hand-written XML Server design; .rnrproj and label text files are the only files edited directly
    Copilot changes only elements you allow, and you can revert them MCP server: scope check and checkpoint before every agent write
    Copilot's server process cannot read business data xpp/data exists only with --allow-data, which the MCP server never gets
    The agent never sees database credentials xpp_query_data runs in the extension's process
    Credentials are not written to settings, logs or files VS Code secret storage; the data service gets them per request and never stores or logs them
    Microsoft's assemblies are never redistributed Build references with <Private>false</Private>; the release fails when a Microsoft DLL is in the output

    Workspace trust and machine settings¶

    • capabilities.untrustedWorkspaces.supported is false. F&O Studio does not run in Restricted Mode, because it runs the compiler, debugger and metadata server for the workspace's projects.
    • Settings that point at programs F&O Studio runs have machine scope, so a workspace's .vscode/settings.json cannot set them: xpp.pacPath, xpp.debuggerProxyPath, xpp.build.msbuildPath and xpp.trace.manifestFolder.
    • pac runs without a shell (unless it is a .cmd shim), and quotes in its arguments are refused.

    Writes to metadata¶

    Every bridge action is registered with a WriteKind (see Bridge-Protocol). Before the handler runs, the dispatcher checks:

    Kind Check Refusal message (example)
    Edit The existing element must belong to one of your custom models (skipped for checkOnly) AxTable 'CustGroup' belongs to <model>, which you can't change. Create an extension in your model instead.
    Create, Copy The target model must be one of your custom models Model '<model>' is not one of your custom models. Create objects in your own model.
    Read none

    Because the check sits in the dispatcher, it applies equally to the designers, the code view, refactorings and every agent tool that delegates to a bridge action. Elements of standard models open read-only in the designers; the editor title offers Create Extension instead.

    Label writes are checked separately: label text files are written only under the custom metadata folder, and label file IDs and languages are validated before any path is built. Names of new elements are validated, so traversal (..\..\), absolute paths, markup and control characters are refused; method source is stored literally (a ]]> inside a string stays text).

    Copilot: scope, checkpoints and activity¶

    The MCP server Copilot uses is started with --activity-log. In that process only:

    1. Scope. Before an Edit or Create action, the server reads %LOCALAPPDATA%\XppVsCode\agentSession.json, written by the extension when you run Set Copilot Scope…. An existing element outside the scope is refused with a message that lists the allowed elements. A new element is allowed and joins the scope.
    2. Checkpoint. While a checkpoint is open (Start Copilot Checkpoint), the server saves each element's state before its first change under checkpoints\<id>\. Revert Copilot Changes Since the Checkpoint… restores them through the metadata API; elements that did not exist are removed. Checkpoint ids must match ^[A-Za-z0-9-]{1,64}$, so an id cannot be a path.
    3. Activity. Every tool call is logged to activity.jsonl (tool, arguments cut to a maximum length, duration, success), with a copy of your element before and after a write, for the Copilot Activity view and its diffs.

    Listing and reverting checkpoints is only available in the extension's own process (--allow-data); the MCP server answers "Not available in this process."

    See Copilot-Checkpoints-and-Scope and Copilot-Activity.

    Team rules and instructions¶

    .xpp/agent-rules.md is appended to the server's instructions (up to 20,000 characters) after the built-in rules, which say to follow the team rules where they are stricter. It refines the agent's behaviour; it does not change what the server enforces. See Team-Rules.

    Agents and production¶

    The generated Copilot agents share a rule: they change data, setup or metadata only after you allow it, and only in development, sandbox or build environments, never in production. This is an instruction to the model; the hard limits are the server checks above.

    Business data¶

    • Where: the business database of the active environment: the local AxDB with Windows authentication on cloud-hosted and VHD environments, or a UDE's Azure SQL database with temporary credentials.
    • Credentials: Request Database Credentials calls the Dataverse action msprov_getfinopssqljitaccessasync (the same request Visual Studio makes), with the role Reader unless Writer is asked for explicitly. The result is kept per environment in VS Code's secret storage (Windows Credential Manager) until it expires.
    • Transport: the connection travels with each xpp/data request to the extension's server process. The server never stores or logs it.
    • Read-only by default: ReadOnlySql accepts a single SELECT (or WITH ... SELECT), ignoring keywords inside strings, quoted identifiers and comments. The data service also runs read-only batches in a transaction it always rolls back. Writes happen only when you turn on Allow changes in the SQL panel, with a confirmation each run.
    • Copilot: xpp_query_data is a VS Code language model tool, not an MCP tool. VS Code asks you to confirm each query ("Run a read-only query on the environment database"), showing the SQL. It runs read-only and rolled back, 50 rows by default and 500 at most, with output capped at 20,000 characters. The connection and credentials stay in the extension.

    See Database-Access and SQL-Query-Panel.

    Network access¶

    Call When
    Microsoft sign-in Through VS Code's Microsoft account provider; optionally with your own Entra app (xpp.auth.clientId)
    Dataverse Web API of your environment Deploy, sync, tests, credentials, setup
    Power Platform developer tools service Connect to Environment (metadata and tool downloads)
    Microsoft Learn xpp_search_docs only: https with the exact host, default port and no user info, checked on the URL and on every redirect
    nuget.org Report Viewer runtime, only after you accept Microsoft's licence
    Public address service To fill in the address for database credentials
    GitHub Report a Problem… when you file the report as an issue

    F&O Studio sends no telemetry. xpp.usageStatistics counts commands in VS Code's local state only; nothing is sent. Try Data Entity and Try Service Operation save requests as .http files without the access token.

    Hardening against hostile input¶

    The server treats input from agents and webviews as untrusted:

    • Designer node paths, label file IDs, checkpoint ids and folders from callers are validated; wrapper_drift reads only a PackagesLocalDirectory.
    • Report RDL with a DTD is refused (no external entities). render_report does not overwrite an existing file unasked and refuses network paths; xpp_measure_image reads PNG images only and refuses network paths.
    • Cross-reference queries use parameters; SQL in element names is data.
    • Regular expressions in Search Code have a match timeout and the whole search a time limit.
    • Every JSON response escapes all control characters, so a response is always one valid line; malformed JSON, deep nesting and very large payloads do not stop the server.
    • Webviews use a Content-Security-Policy with nonces from crypto.randomBytes.

    How it is tested¶

    node scripts/security-probes.js --model <your custom model> runs dynamic probes against the built server. Every probe must pass after a server change.

    Area Examples of probes
    Object names traversal, absolute paths, markup, NUL, 5,000-character and empty names are refused; no file is written outside the metadata tree
    Ownership create_object in a standard model, update_object and xpp_update_object on Global, designer edits on CustGroup are refused
    Method source a CDATA break-out is stored literally
    Designer paths .. segments and very deep paths are refused
    Labels traversal in label file IDs and languages reads nothing; CRLF label IDs and standard label files are refused
    Checkpoints and drift traversal checkpoint ids, wrapper_drift on a non-package folder, references on standard models are refused
    Reports standard report designs are not written; DTDs, network paths and overwrites are refused; images only
    Agent tools SQL injection in names is data; catastrophic regex is bounded; non-Learn URLs, file:, metadata endpoints and other ports are refused
    Protocol malformed JSON, 20,000-level nesting, a 5 MB payload and unknown methods; the server stays up and every response is valid JSON

    Probes on standard objects carry a payload the handler rejects before saving, so even a missing ownership check cannot change standard metadata. Unit tests in test/server check the write policy through the dispatcher. Review findings and their status are in docs/review-findings.md. See Testing-the-Extension.

    Code signing and supply chain¶

    • The server exe in the published extension is built from the public source on GitHub Actions and signed through SignPath (certificate by SignPath Foundation) when signing is configured; each signing request is approved by hand. The Marketplace signs the extension package.
    • Microsoft's compiler package is used only to compile the server during the build, from a private feed; it is never part of the repository or the extension.
    • Pdb2Pdb is downloaded at a pinned version and checked against a pinned SHA-256.
    • The extension has no runtime npm dependencies.

    See Release-Process.

    Limitations¶

    • The policy protects metadata and files F&O Studio writes. It does not limit what you do yourself in the SQL panel with Allow changes, or what X++ code you run with Run Snippet in Environment in a development environment.
    • The "never in production" rule of the agents is an instruction; use development environments and database Reader credentials for agent work.
    • Code you build and deploy runs with the environment's permissions; review it as usual (Review-My-Changes, Pre-Deploy-Checklist).
