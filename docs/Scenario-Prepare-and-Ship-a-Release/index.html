    Scenario: Prepare and ship a release¶

    This walkthrough is for the developer or lead who takes a finished change set from a feature branch to a deployable package. At the end you have a change set that builds without errors, passed best practice, performance and security checks, ran its tests on a unified developer environment (UDE), and a deployable package (.zip) with a version number that your release process can take to a sandbox and, later, to production.

    F&O Studio covers everything up to and including the package and the deploy to development and test environments. Uploading the package to Lifecycle Services (LCS) or the Power Platform admin center and the production deployment follow your team's process outside F&O Studio.

    The situation¶

    Your team works in the model ContosoExtensions (package ContosoExtensions) in a Git repository. Sprint work for work item 4711 "Credit review flag on customers" is done on the branch feature/credit-review:

    • a table extension CustTable.ContosoExtensions with a new field ContosoCreditReviewRequired;
    • a form extension CustTable.ContosoExtensions that shows the field on the customer form;
    • a Chain of Command class CustTable_Contoso_Extension that wraps CustTable.validateWrite;
    • a display menu item ContosoCustCreditReviewList and its form ContosoCustCreditReviewList;
    • a privilege ContosoCustCreditReviewListView.

    The release goes to the team's UDE for a test round, then a deployable package goes to the test sandbox. You want to be sure nothing is missing before you hand the package over.

    What you need¶

    • A UDE connected with Connect to Environment… (see Connect to Environment), or a cloud-hosted or VHD environment (see Cloud-Hosted and VHD Environments). Deploy, Run Tests and Synchronize Database through Dataverse are UDE-only.
    • The D365FO project of the change open (Open D365FO Project…, see D365FO Projects). The Pre-Deploy Checklist needs it.
    • Your model folder in a Git repository. Review My Changes and Show Changed Elements read Git. If the packages are linked into the metadata folder with junctions (as Open Team Repository… sets them up), F&O Studio follows the links to the repository.
    • Optional: xpp.git.baseBranch set to your main branch (for example main), so you are not asked every time.
    • Optional: GitHub Copilot, for the F&O Release Manager agent and its tools.

    Step by step¶

    Phase 1: Know exactly what ships¶

    1. Run Show Changed Elements from the command palette (category F&O Studio). It lists every element of your models that changed in Git: uncommitted changes, plus everything the branch changed since it left xpp.git.baseBranch. Each entry shows the element type, the Git letter (M modified, A added, D deleted, R renamed) and (branch) when the change is already committed. Pick an entry to open its designer. See Show Changed Elements.
    2. Compare the list with what you expect. In the example you expect the five elements above. If you see an element you did not mean to change (for example a label file touched by accident), fix it in Git before you go on.
    3. Look at the project view. It marks changed elements with the same letters and Git colours, so you can spot uncommitted work. See Git Changes in the Project View.
    4. Make sure the commits name the work item. Run Link Work Item… (Dynamics 365 view > Deploy, or the command palette) and enter 4711. F&O Studio adds #4711 (Azure Repos) or AB#4711 (GitHub linked to Azure Boards) to the commit message box of the Source Control view. Review My Changes later lists the work items it finds in the branch's commit messages. See Azure DevOps and GitHub Integration.

    Phase 2: Review the change set¶

    1. Run Review My Changes (project view check menu, Dynamics 365 view > Build and check, or the command palette). It asks "Compare with this branch (empty: only uncommitted changes)" with xpp.git.baseBranch (or main) filled in. Press Enter.
    2. The report opens in the Results view with four sections:
    3. Pull request summary: the changed elements by type, the security impact (roles, duties or privileges that changed), new menu items that need a privilege, and the work items found in the commit messages.
    4. Chain of Command: wrappers that wrap a base method but never call next. In the example, if CustTable_Contoso_Extension.validateWrite forgot next validateWrite(), it shows here as an error, because the standard validation would be skipped.
    5. Best practice and compiler: xppbp results for the changed elements, plus errors and warnings in Problems.
    6. Performance: warnings of the static performance rules on changed classes, tables, forms and data entities.
    7. Click a finding to open the element at the method and line. Fix, save, then use Run Again on the report.
    8. When it is clean, use Copy Report as Markdown and paste the pull request summary into the pull request description. See Review My Changes and Results View.

    Phase 3: Build and check¶

    1. Run Build Project (Ctrl+Shift+B in an X++ editor, or click the project item in the status bar). Unsaved code views are saved first when xpp.build.saveBeforeBuild is on (the default). Errors go to the Problems view at the right line; a failed build offers Show Problems. See Build Project and Model and Compiler Diagnostics.
    2. Before a release, also run Build Model once. Build Project reports only the project's problems; Build Model covers every element of the model, including ones that are not in the project.
    3. Run Run Best Practice Checks on Project. It runs xppbp, the checker Visual Studio runs, and puts the warnings in Problems. The status bar shows the error and warning count for a few seconds. See Best Practice Checks.
    4. Run Analyze Performance on the classes that do real work (right-click in the project view, or from the code editor's context menu). In the example, check CustTable_Contoso_Extension and the list form. See Analyze Performance.
    5. Run Find Security Gaps (Security view title bar or Dynamics 365 view > Security). Pick ContosoExtensions. An error such as a menu item that no privilege covers blocks the release. In the example the new menu item must be in ContosoCustCreditReviewListView; if it is not, right-click the menu item and run Add to Privilege…. See Find Security Gaps and Add to Privilege.
    6. If the change wraps standard methods or the environment was updated recently, run Upgrade Readiness on the model (right-click the model in the Application Explorer, or Dynamics 365 view > Build and check). See Upgrade Readiness.

    Phase 4: Run the Pre-Deploy Checklist¶

    1. Run Pre-Deploy Checklist (project view check menu or Dynamics 365 view > Build and check). It runs, in order, for the open project's model:
    Step What it checks Blocks the release
    Build Builds the project's elements Yes, when the build fails
    Best practice xppbp on the project's elements Yes, when there are errors
    Performance Static performance warnings on classes, tables, forms and entities No, it reports the count
    Security Security gaps of the model (xpp_analyze_security with op=gaps) Yes, for gaps of severity Error
    Scratch code Run Snippet's scratch class <Model>ScratchRunner left in the model Yes
    Tests Reminder: run tests after deploying (UDE), or on the VM (cloud-hosted, VHD) No
    1. The report opens in the Results view with a pass or fail per step and the headline "Ready to package and deploy." or "Not ready: fix the failed steps first." See Pre-Deploy Checklist.
    2. If the scratch code step fails, open the project view and Delete the ContosoExtensionsScratchRunner class that Run Snippet in Environment left in the model. It would otherwise ship in the package. See Run Snippet.
    3. When every blocking step passes, F&O Studio shows "The checklist passed." with Create Deployment Package and, on a UDE, Deploy. Choose Deploy first if you want a test round on the UDE.

    Phase 5: Deploy to the team's UDE and test¶

    1. Run Deploy Models to Environment (in the Dynamics 365 view it is "Deploy Models to Online Environment…" under Deploy). F&O Studio deploys the packages as they were built on this machine, through the environment's Dataverse, as Visual Studio does. Nothing is recompiled. See Deploy to Environment.
    2. Pick the packages under "Packages to deploy (as built on this machine)". Your project's package is preselected.
    3. Pick the database sync under "Database sync after deploy":
    4. None: no sync. Use it when no table, view or entity changed.
    5. Module: synchronizes the tables of the deployed packages. In the example the new field on CustTable needs at least this.
    6. Full: synchronizes the whole database. Slow; use it only when you have a reason.
    7. Watch the X++ Deploy output. Before uploading, F&O Studio builds and copies the C# projects the X++ project references, and converts the PDBs to portable PDBs so the debugger can read them.
    8. If you deployed with None and later find you need a sync, run Synchronize Database and choose Full or Module. See Synchronize Database.
    9. Check the status bar. The project item shows when the build is newer than the last deploy from this machine. Run Tests, the debugger and Verify Changes in the Running App warn you about that and offer Deploy First. See Status Bar.
    10. Run the tests: Run Tests from the project view check menu, or the VS Code Test Explorer. Tests run against the deployed code on the environment. See Run Tests and Test Explorer.
    11. Optional (preview): run Verify Changes in the Running App (Copilot). It turns the changed menu items, form extensions and entity extensions into check steps (for example "Open form CustTable (through its menu item) and find the controls ...") and opens Copilot agent mode to run them with the Dynamics 365 ERP MCP server, read-only. See Verify Changes in Running App.

    Phase 6: Create the deployable package¶

    1. Make sure the last build is the one you want to ship. Create Deployment Package uses the package as built.
    2. Run Create Deployment Package… (Dynamics 365 view > Deploy, or the command palette).
    3. Answer the three prompts:
    4. Create deployment package: packages: pick ContosoExtensions (you can pick several of your packages).
    5. Package version: defaults to 1.0.0.0; it must have four parts. Use your release number, for example 1.4.0.0.
    6. Output folder for the deployable package: a folder outside the metadata folder, for example a drop folder.
    7. F&O Studio runs RunPackageCreationAll.ps1 from the platform bin folder, the same script Visual Studio's Create Deployment Package runs, as a VS Code task named "Create deployment package". Watch the terminal for errors. See Create Deployment Package.
    8. Take the package to the next environment the way your team does it (for example upload to the LCS asset library, or the Power Platform admin center). This step is general D365FO practice; F&O Studio does not upload or apply packages to sandbox or production. See Environments and Promotion.

    Phase 7: Document the release¶

    1. If roles, duties or privileges changed, run Security Report… and choose Roles of model… > ContosoExtensions and Markdown ("sign-off document") or CSV ("for Excel"). Attach it to the release for the security sign-off. See Security Report.
    2. In the Results view, use Export Report… on the Pre-Deploy Checklist and the Review My Changes report and keep them with the release.
    3. Ask the F&O Release Notes agent for user-facing notes (see below).

    Repeating releases with tasks¶

    For the build and deploy part you can use tasks in .vscode/tasks.json instead of the commands. The deploy task deploys the package of the open project's model without asking which packages:

    {
  "version": "2.0.0",
  "tasks": [
    { "type": "xpp", "action": "buildModel", "label": "Build model" },
    { "type": "xpp", "action": "deploy", "dbSync": "Module", "label": "Deploy with module sync",
      "dependsOn": "Build model" }
  ]
}

    dbSync takes None, Module or Full. See Build Tasks.

    On cloud-hosted and VHD environments¶

    • Deploy Models to Environment and Run Tests are hidden; the environment runs what you build. After a successful build, F&O Studio restarts the running AOS hosts so they load it (xpp.build.restartLocalAos).
    • Synchronize Database (command palette) runs a full sync of the local AxDB; Synchronize Table(s) with the Database syncs only the project's tables.
    • The Pre-Deploy Checklist tells you to run tests on the VM. Create Deployment Package works the same way.

    Doing it with Copilot¶

    Pick F&O Release Manager in the Copilot agent picker. It runs the checks, summarizes the change set with its risk and creates the package when you ask. It changes nothing and deploys nowhere without your permission, and only to development, sandbox or build environments, never to production.

    Example prompts:

    • "Prepare the ContosoExtensions model for release. Compare the branch with main, run the build, best practice and security gaps, and give me a release summary with risks."
    • "The checks passed. Create the deployable package for ContosoExtensions with version 1.4.0.0."
    • "Which of the changes need a database sync, and which change security?"

    What the agent does:

    Step Tool
    Lists the changed elements against the base branch xpp_diff_changes
    Builds each model to release xpp_build
    Runs best practice xpp_check_best_practice
    Runs the tests on the UDE (it warns when the deployed code is older than the build) xppRunTests
    Checks security gaps xpp_analyze_security with op=gaps
    Creates the package, only when you asked for one xpp_package

    Checkpoints for you:

    • Read the release summary: checks with results, changes with their risk (data model changes that need a sync, security changes, integrations, upgrade risks), package path, deployment steps and rollback notes.
    • The agent's tool calls show in the Copilot Activity view with their arguments and results. See Copilot Activity.
    • Before that, hand the branch to F&O Code Reviewer ("Review the changes on this branch against main"); its handoff Prepare the release brings you back to the Release Manager.
    • After the release, use the handoff Write release notes, or pick F&O Release Notes and ask: "Write release notes for the changes on feature/credit-review for the accounts receivable team." It groups the changes by business process and audience, with new setup and training notes.

    See Agents for Developers and Copilot Agents.

    Checklist¶

    • [ ] Show Changed Elements lists only the elements you meant to change.
    • [ ] Commits name the work item (Link Work Item…).
    • [ ] Review My Changes: no Chain of Command wrapper without next, no best practice errors, performance warnings understood.
    • [ ] Build Model succeeds without errors.
    • [ ] Run Best Practice Checks on Project: no errors.
    • [ ] Find Security Gaps: no errors; every new menu item is in a privilege.
    • [ ] Pre-Deploy Checklist: "Ready to package and deploy."
    • [ ] No Run Snippet scratch class in the model.
    • [ ] Deployed to the UDE with the right database sync; tests pass against the deployed code.
    • [ ] Deployable package created with the right version from the last build.
    • [ ] Security report and release notes attached to the release.
