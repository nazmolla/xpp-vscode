    Agents for Functional Consultants¶

    F&O Studio includes nine Copilot agents written for functional consultants and key users. They answer in business terms (menu paths, fields as labelled in the client, setup and data) and show X++ only when you ask. They read the application's metadata with the F&O Studio tools when a development environment is connected, and look at the running environment through Microsoft's Dynamics 365 ERP MCP server. Four shared agents (Solution Designer, Architect, Security & License, Integration) also serve consultants; they are described on Agents for Developers.

    For how agents are picked and routed, see Copilot Agents.

    When to use them¶

    • You need to know what a field, parameter or process does and which setup drives it.
    • A user reports an error or an unexpected result, and you want the setup or data cause and the fix.
    • You need to explain why a sales order, invoice, voucher or item looks the way it does.
    • You are designing roles, writing test scenarios, running a fit-gap, planning a data migration or writing release notes.

    Before you start¶

    Need Why
    VS Code with GitHub Copilot, chat in agent mode The agents are Copilot custom agents.
    F&O Studio installed It contributes the agents.
    Dynamics 365 ERP MCP server connected (recommended) Lets the agents read setup, open forms and read data in the running environment. Microsoft's setup page: Use the Dynamics 365 ERP MCP server in VS Code.
    A development environment connected in F&O Studio (optional) Makes the F&O Studio tools (xpp_*) available: the agents can then read forms, tables, labels and the code behind a behaviour. See Connect to Environment.
    Database access (optional) On a development environment, xppQueryData reads the business database with one read-only SELECT. See Database Access.

    Working without a development environment¶

    You can use most functional agents without a development environment. Explainer, Setup Advisor, Data Investigator, Functional Triage, Test Scenarios, Fit-Gap Analyst and Data Migration then work from the live environment and documentation (xpp_search_docs when available, otherwise Microsoft Learn on the web), and say that metadata-based checks were skipped. Role Designer and Release Notes rely on the F&O Studio tools (xpp_analyze_security, xpp_diff_changes), so they need a development environment for a full answer.

    The Dynamics 365 ERP MCP server¶

    The ERP MCP server is Microsoft's MCP server for Finance & Operations. F&O Studio does not install or configure it. When it is connected, the agents use its tools to see the environment as users see it:

    Tools Used for
    data_* Find and read records through data entities (and, when allowed, create, update or delete them)
    form_* Open menu items and forms, read controls, filter grids, open lookups
    api_* Find and invoke actions

    When it is not connected, the agent suggests connecting it, or opens the environment with the browser tools.

    The rule about changes¶

    Only two functional agents may change anything: F&O Setup Advisor and F&O Data Migration. They follow this rule:

    • They create, change or delete data, setup, security or metadata only after you explicitly allow that change.
    • Only in a development, sandbox or build environment, never in production.
    • If they don't know which kind of environment it is, they ask, and treat it as production until you answer.
    • Where they may not change something, they describe the change: the menu path and the values to enter.

    All other functional agents are read-only. They recommend changes and offer the next agent.

    Always tell the agent which environment you are connected to, for example "This is the UAT sandbox" or "This is production; read only".

    F&O Functional Explainer¶

    Explains the system to a functional consultant or key user.

    How it works:

    1. Finds the form, field or process (xpp_find_object, xpp_get_form_layout for what the form shows, xpp_read_label).
    2. Reads the logic behind it (xpp_read_object, xpp_find_references) to know which parameters and setup it uses and when, and translates that into business rules.
    3. Confirms with Microsoft Learn (xpp_search_docs) and, when connected, the actual setup in the live environment.

    Output: a short explanation: what it does, the setup that drives it (menu path, field, values), examples and exceptions.

    Example prompts:

    What does the "Credit limit type" parameter in Accounts receivable parameters do?

    On the customer group form, what is the "Terms of payment" field used for when a sales order is created?

    When does a sales order line get its warehouse from the item and when from the customer?

    F&O Setup Advisor¶

    Reviews configuration and says what to fix. It may change setup only with your permission and never in production.

    How it works:

    1. Reads the setup in the live environment: parameters forms, number sequences, posting profiles, groups, defaults, per legal entity.
    2. Knows what each setting does (xpp_read_object on the parameters table and the code that reads it, xpp_search_docs) to judge its impact.
    3. Compares against what the process needs, or against another legal entity or environment when you ask.

    Output: a checklist: setting (menu path), current value, expected value, impact, fix.

    Example prompts:

    Check the Accounts receivable setup in legal entity USMF for invoicing sales orders. This is a sandbox; read only.

    Compare the number sequences of USMF and DEMF for sales orders and invoices.

    F&O Data Investigator¶

    Investigates data, one record at a time.

    How it works:

    1. Finds the record and its related records (lines, transactions, vouchers, inventory dimensions, settlements) in the live environment, or with xppQueryData on a development environment. It uses the table relations (xpp_read_object) to join correctly and filters by company (DataAreaId).
    2. Finds the setup and code that produced the values (defaults, posting, price and discount logic) with the F&O Studio tools.
    3. Keeps queries narrow: specific records, few columns, row limits.

    Output: what happened to the record, step by step, with the evidence (records, fields, values) and the setup or action that caused it; how to correct it, if needed.

    Example prompts:

    Sales order SO-000123 in USMF has a line discount of 10% that nobody entered. Why?

    Why did invoice CIV-000045 post to main account 130100 instead of 130200?

    See also Scenario: Investigate Why a Record Looks Wrong.

    F&O Functional Triage¶

    First line for a user's error or unexpected result.

    How it works:

    1. Gets the exact message and context (form, action, company, record).
    2. Runs xpp_find_message_source. For "Field '...' must be filled in." the platform checks a mandatory field: the agent finds which field on the form or entity is empty. Otherwise it reads the condition in the raising code and translates it into setup and data.
    3. Checks that setup or data in the live environment.
    4. If the cause is a code defect, says so and hands off to F&O Support.

    Output: the cause in one sentence, evidence, the fix (menu path and values), and how to avoid it next time.

    Example prompts:

    A user gets "Field 'Customer group' must be filled in." when creating a customer in USMF. What's missing?

    Posting a vendor invoice fails with "The posting profile is not set up". The vendor is in group 10.

    See also Find Message Source and Scenario: From Error Message to Fix.

    F&O Role Designer¶

    Designs security roles from job descriptions.

    How it works:

    1. Lists the tasks the job needs (menu items, view or maintain) and the ones it must not have.
    2. Finds standard roles and duties that cover them (xpp_analyze_security with op=access and op=placement), preferring reuse over new privileges.
    3. Checks the license (op=license) and conflicts (op=sod), and proposes read-only access where it lowers the license.

    Output: the role design: roles and duties to assign, duties or privileges to add or remove, license per role, conflicts and mitigations. Building new security elements goes to the F&O Developer.

    Example prompts:

    Design a role for a sales clerk who enters and confirms sales orders but must not post invoices or change prices.

    Can a user with TradeSalesClerk get by with a cheaper license if we remove maintain access on customer groups?

    See also Scenario: Design a Security Role and Reduce License Cost.

    F&O Test Scenarios¶

    Writes test cases a key user can run.

    How it works:

    1. Identifies the process and the changed behaviour (from the requirement, the design, or xpp_diff_changes).
    2. Finds the forms and fields involved (xpp_get_form_layout) so steps use the client's labels and menu paths.
    3. Covers the happy path, variations (setup, legal entity, dimensions), negative cases (validations) and regression of the standard process.

    Output: a table per scenario with ID, title, preconditions and test data, steps (menu path, action, values) and expected result; optionally a Task Recorder outline.

    Example prompts:

    Write test scenarios for the new credit hold reason on customer groups, including negative cases.

    Write regression scenarios for sales order confirmation after the changes in this branch.

    F&O Fit-Gap Analyst¶

    Classifies requirements against standard D365FO.

    How it works: for each requirement, it searches Microsoft Learn (xpp_search_docs) and the standard application (xpp_find_examples, xpp_find_object) for the feature, checks feature management and parameters, and estimates the gap.

    Output: a table with ID, requirement, fit (Standard, Configuration, Extension, ISV, Process change), how it's met (feature, menu path, or the gap), evidence (doc link or element), complexity (Low, Medium, High) and notes; then a summary and the gaps to design next.

    Example prompts:

    Fit-gap these requirements:
1. Block sales orders for customers over their credit limit.
2. Print the customer's VAT number on the invoice.
3. Approve purchase requisitions above 10,000 by two managers.

    F&O Data Migration¶

    Plans and troubleshoots data migration with data management. It may change data only with your permission and never in production.

    How it works:

    1. Finds the entities per data area (xpp_list_objects on AxDataEntityView, or the entity list in the environment) and reads their fields, mandatory fields, natural keys and staging (xpp_read_object).
    2. Orders the loads by dependency (setup before masters before open transactions), per legal entity.
    3. For import errors, reads the error, finds its source (xpp_find_message_source; for "must be filled in" it lists the mandatory fields) and the staging record.

    Output: a migration plan (entity per data area, keys, required fields, sequence, templates and validation steps), or for errors, the cause and the corrected data.

    Example prompts:

    Plan the migration of customers: groups, customers, addresses, contacts and open balances for USMF.

    The customer import fails with "Field 'Customer group' must be filled in." for 30 rows. What's wrong with the file?

    See also Scenario: Expose Data to an Integration.

    F&O Release Notes¶

    Explains a release to the people who use the system.

    How it works:

    1. Lists the changes (xpp_diff_changes, commit messages and linked work items) and reads enough of each to know the user-visible effect (forms, fields, validations, reports, security).
    2. Groups them by business process and audience.

    Output: release notes per process: what changed and why, who is affected, new or changed setup (menu path), and training or communication notes. No technical jargon.

    Example prompts:

    Write release notes for this branch for the accounts receivable team.

    A typical consultant flow¶

    F&O Functional Triage    "Users in USMF get 'Field 'Customer group' must be filled in.' when they create customers."
   -> (setup cause found)
F&O Setup Advisor        "Check the setup described above in the environment."
   -> Explain a record
F&O Data Investigator    "Investigate a record affected by the setup above."

    If Triage finds a code defect, it hands off to F&O Support (a developer agent) with Investigate in code.

    Limitations¶

    • Live checks need the Dynamics 365 ERP MCP server, which you set up separately. Without it, the agents fall back to the browser tools or describe what to check.
    • Without a development environment, metadata-based checks (forms, fields, code behind a behaviour) are skipped; the agent says so.
    • Read-only agents are read-only by instruction. Tell agents the environment type, and never give production write permission you don't intend.
