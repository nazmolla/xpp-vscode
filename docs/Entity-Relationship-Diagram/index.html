    Entity Relationship Diagram¶

    View Entity Relationship Diagram (ERD) draws a table and its related tables as boxes with their key fields, connected by the table relations with their cardinality. You choose how many levels of related tables to follow, whether to follow the table's own relations, the relations of other tables to it, or both, and whether to show key fields or all fields. You can export the diagram as SVG or as a Mermaid ER diagram. Visual Studio has no ERD for F&O tables.

    When to use it¶

    • Understand the data model around a table before you write a query, a data entity or an integration, for example what CustTable refers to.
    • Find which tables refer to a table (incoming relations), for example everything that points at CustGroup.
    • Document a feature's data model: export the diagram to SVG for a design document or to Mermaid for a Markdown page or wiki.
    • Check the relations of your own new tables.

    Before you start¶

    • F&O Studio is connected to an environment with metadata (UDE, cloud-hosted or VHD). The diagram is built from local metadata; it does not need the cross-reference database or the environment.
    • The first diagram with incoming relations scans all table and table extension files once (see How it works); later diagrams use the cached index.

    How to use it¶

    Opening the diagram¶

    Place How
    Application Explorer or project view Right-click a table > View Entity Relationship Diagram (ERD)
    Element designer of a table Right-click the table node > View Entity Relationship Diagram (ERD)
    Command Palette F&O Studio: View Entity Relationship Diagram (ERD), then pick a table

    The diagram opens in a tab titled ERD: <table>. Running the command again for the same table brings that tab to the front.

    Reading the diagram¶

    • Tables are laid out in columns by level: the starting table in the middle, tables it refers to (outgoing) to the right, tables that refer to it (incoming) to the left. Each column is sorted by name and centred vertically.
    • The starting table has a highlighted header. Tables of your own models have a green border.
    • Each box lists fields with their type (EDT, enum or base type) on the right. Primary key fields are bold with a key symbol. The primary key is the fields of the table's primary index; a table without one (or with the surrogate key) shows RecId.
    • Each curve is a relation, drawn from the field it uses in one table to the related field in the other, with an arrow at the related table. The small labels at both ends show the cardinality (0..*, 1..*, 0..1, 1). Hover a curve to see the relation name and its field pairs, for example CustTable.CustGroup → CustGroup / CustGroup = CustGroup.CustGroup.
    • Hover a box to see the table name and its model.
    • The status line shows the number of tables and relations.

    Working with the diagram¶

    • Click a table to open it in the Element Designer.
    • Double-click a table to make it the starting table: the diagram is rebuilt around it and the tab title changes.
    • Change the toolbar options; the diagram is rebuilt at once:
    Option Values
    Levels 1 to 5 levels of related tables from the starting table
    Relations Outgoing (tables it refers to), Incoming (tables referring to it), Both
    Fields Keys and relation fields (primary key plus the fields the drawn relations use), All fields
    • Export SVG… saves the diagram as a standalone SVG (the current theme's colours are written into the file, on the editor background).
    • Export Mermaid… saves a Mermaid erDiagram as .mmd, or as .md wrapped in a ```mermaid block.
    • Copy Mermaid copies the Mermaid text to the clipboard.

    Mermaid output¶

    The Mermaid text has one line per drawn relation and one block per table with the shown fields, marked PK and FK. A shortened example:

    erDiagram
    CustTable }o--|| CustGroup : "CustGroup"
    CustTable {
        CustAccount AccountNum PK
        CustGroupId CustGroup FK
    }
    CustGroup {
        CustGroupId CustGroup PK
    }

    The type of a field is its EDT, else its enum, else its base type (str, ...). The relation's cardinality and related table cardinality map to Mermaid's crow's foot symbols.

    Size limit¶

    A diagram shows at most 60 tables. When the levels and direction would reach more, the status line says "limited to 60 tables, lower the levels". Lower the levels, or switch from Both to one direction.

    Options and settings¶

    The settings set the toolbar defaults for new diagrams:

    Setting Default Effect
    xpp.erd.depth 1 Levels of related tables to follow (1 to 5)
    xpp.erd.direction outgoing outgoing: tables the table refers to (its relations); incoming: tables that refer to the table; both
    xpp.erd.fields keys keys: primary key and the fields of the drawn relations; all: all fields

    Changes in the toolbar apply to the open diagram only.

    How it works¶

    • The panel is src/erd.ts. It collects the tables level by level, then draws them in the webview as SVG.
    • Bridge action table_erd (TableRelationsService.cs) returns, for up to 40 tables per request: label, model, whether the model is yours, table group, primary index and key fields, all fields (including fields of table extensions) with their type, and all relations (including relations added by table extensions) with related table, cardinalities, relationship type and constraints.
    • Outgoing follows the relations of each table. Incoming asks bridge action incoming_relations for the tables whose relations name the table. That action uses an index built by scanning every AxTable and AxTableExtension XML file of the reference and custom metadata folders for <RelatedTable> inside <Relations>. The index is kept in memory and in %LOCALAPPDATA%\XppVsCode\cache\relations-<hash>.json, and is rebuilt when the folders change.
    • Only relations of tables whose relations were followed (outgoing) or into tables whose incoming relations were followed are drawn, so the diagram shows the paths it explored.
    • Table details are cached for the lifetime of the tab, so changing options or re-centring is fast.

    Limitations¶

    • Tables only. Views, data entities and maps are not drawn.
    • At most 60 tables and 5 levels.
    • Relations are drawn from the relation constraints with fields; fixed-value constraints are not shown on the curve.
    • The layout is by level, not optimized to avoid crossing lines.

    Troubleshooting¶

    Symptom Cause Fix
    "Table '' not found." The table is not in the metadata of the active environment Check the name and the environment (Select Environment)
    The first diagram with Incoming or Both takes a while The relation index is being built from all table files Wait; later diagrams use the cache
    "limited to 60 tables, lower the levels" The diagram reached the limit Lower Levels or use one direction
    A new relation of your table is missing in Incoming of the other table The cached index is from before the change It is rebuilt when the table folders change; reopen the diagram
