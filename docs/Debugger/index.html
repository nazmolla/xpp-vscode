    Debugger¶

    F&O Studio debugs X++ in VS Code's own debugger: breakpoints, stepping, variables, the call stack, the Debug Console and the Infolog. On a unified developer environment (UDE) it attaches to AXHost.exe in the cloud through Microsoft's debugger proxy, exactly the way Visual Studio's Launch Debugger does. On cloud-hosted and VHD environments it attaches to the local AOS with the C# extension's .NET debugger, the way Visual Studio's F5 does. You set breakpoints in the X++ code view of your own elements and of standard elements, and in the C# code your project references.

    This page is the overview. The details are on separate pages:

    Page What it covers
    Breakpoints and Source Mapping How a breakpoint in the code view reaches the compiled code, debug source files, PDB document names
    Debugging Standard Code Breakpoints in Microsoft's elements (for example PurchTable.init), module loading, Just My Code
    Debugging C# Code Breakpoints in the C# assemblies your X++ project references
    Debugging on Cloud-Hosted Cloud-hosted and VHD environments: local AOS, IIS or IIS Express, Batch.exe, portable PDBs
    Infolog The Infolog view: messages raised by the code you debug
    Debugger Options launch.json options and the xpp.debuggerProxyPath setting

    When to use it¶

    • You want to see why a class, table method or form method behaves the way it does on a running environment.
    • You want to stop in standard code (for example the init method of the PurchTable form) to understand what it does before you extend it.
    • You need the Infolog messages that the code raises while you step through it.
    • Your X++ project calls a C# library and you want to step into it.

    Before you start¶

    • An environment selected. Run F&O Studio: Select Environment… (or F&O Studio: Connect to Environment… for a new UDE). See Select Environment and Connect to Environment.
    • A UDE: the FinOps tools that Connect to Environment… downloads contain the debugger proxy (%LOCALAPPDATA%\Microsoft\Dynamics365\<version>\FinOpsTools\DebuggerProxy\Microsoft.Dynamics.AX.DebuggerProxy.exe). You sign in with your Microsoft account; F&O Studio uses the Dataverse token of that sign-in (Sign-In and Authentication).
    • A cloud-hosted or VHD environment: the C# extension (ms-dotnettools.csharp) is needed; F&O Studio offers to install it. See Debugging on Cloud-Hosted.
    • Built code. Build your model first (Build Project and Model). On a UDE the environment runs the deployed code, so deploy what you built (Deploy to Environment). On cloud-hosted and VHD environments the build restarts the AOS so it loads the new build.

    How to use it¶

    Start the debugger¶

    Start it in any of these ways:

    • Command Palette: F&O Studio: Launch Debugger.
    • Dynamics 365 view: the Debug group has Launch Debugger (and Infolog). The view's title bar also has the Launch Debugger button.
    • Infolog view (in the F&O Studio panel): the Launch Debugger button in its title bar.
    • Run and Debug view: with no launch.json, press F5 (Run > Start Debugging) and pick the X++ debugger, or add a configuration to .vscode/launch.json (see Debugger Options). The configuration snippet is X++: Attach to Dynamics 365, and the configuration it creates is:
    {
  "type": "xpp",
  "request": "attach",
  "name": "Attach to Dynamics 365 (unified developer environment)"
}

    The debugger always attaches. There is no launch request: the environment is already running.

    What happens on a UDE¶

    1. When your project's model was built after its last deploy from this machine, a warning says so and adds "The debugger uses the deployed code." Choose Deploy First to run Deploy Models to Environment (the debugger does not start), or Continue to debug the code that is deployed.
    2. A notification Preparing X++ debugging… shows the steps: signing in, then writing debug sources.
    3. F&O Studio starts the debugger proxy and attaches to AXHost.exe. The Debug toolbar appears.
    4. Use the environment in the browser (open the form, run the class). When the code reaches a breakpoint, VS Code stops and shows the line in the element's X++ code view.
    5. Step (F10, F11, Shift+F11), look at Variables, Watch and Call Stack, and evaluate expressions in the Debug Console as with any VS Code debugger.
    6. Press Continue (F5) or Disconnect when you are done.

    What happens on cloud-hosted and VHD environments¶

    F&O Studio recognises the local environment and attaches to the AOS process on this machine with the C# extension's clr debugger, one debug session per process. See Debugging on Cloud-Hosted.

    Set breakpoints¶

    Open the element's code view (click a class in the Application Explorer, or View Code on a table or form) and click in the gutter, or press F9. That is all: F&O Studio copies each code view breakpoint to the compiled view of the element and reports the copy's state on your breakpoint. A solid red dot means it is bound; a hollow one shows a message when you hover it, for example "Waiting for the symbols to load.". Conditions, hit counts and logpoints work. See Breakpoints and Source Mapping.

    The environment pauses for every user¶

    On a UDE, the debugger stops the server process (AXHost.exe), not just your session. While VS Code is stopped at a breakpoint, or after you press Pause, the environment's server is paused for every user of that environment: pages stop responding until you continue. Continue or disconnect promptly, and do not leave a session stopped.

    F&O Studio protects the environment in several ways:

    • Disconnect resumes first. When you disconnect (or stop) while the server is stopped, F&O Studio sends continue first and only then detaches. The X++ output says "Resuming the environment before the debugger detaches.".
    • It never ends the process. An attached debugger only detaches: terminateDebuggee is always sent as false, on a UDE and on the local AOS. Stopping the debugger never takes the AOS down.
    • Closing or reloading the window resumes and detaches every session, then stops the proxy (after at most about three seconds).
    • A crashed window can leave a debugger proxy running. F&O Studio remembers the proxies it started; when it starts again it stops proxies whose window is gone and logs "Stopped a debugger left attached by a closed window (DebuggerProxy ).". Proxies of other open windows are left alone.

    Options and settings¶

    Where Key Default Effect
    Setting xpp.debuggerProxyPath empty Path to Microsoft.Dynamics.AX.DebuggerProxy.exe. Empty uses the FinOps tools installed by Connect to Environment. Machine scope (a workspace cannot set it)
    Setting xpp.build.restartLocalAos true Cloud-hosted and VHD only: a successful build restarts the running AOS hosts (and detaches the debugger first)
    launch.json justMyCode on (UDE) Keep it on. See Debugger Options
    launch.json additionalModules [] More modules whose symbols load
    launch.json symbolOptions F&O Studio's Replaces the symbol options entirely (UDE)
    launch.json logging vsdbg logging, e.g. { "exceptions": false }
    launch.json processName AXHost.exe Process to attach to; on cloud-hosted and VHD e.g. Batch.exe
    launch.json sourceFileMap Extra source path mappings

    Full details: Debugger Options.

    How it works¶

    The code is in src/debug.ts. F&O Studio registers the debug type xpp ("X++ (Dynamics 365 unified developer environment)") with a configuration provider and a debug adapter factory, plus a tracker on the clr debug type for the local AOS.

    UDE: the debugger proxy is the debug adapter¶

    Visual Studio debugs a UDE through Microsoft.Dynamics.AX.DebuggerProxy.exe (part of the FinOps tools). The proxy has a mode for Visual Studio Code's .NET debugger, vsdbg: it speaks the Debug Adapter Protocol (DAP) on stdin/stdout and tunnels to vsdbg running next to AXHost.exe in the environment, over wss://<environment>/___sidecar/AOS1/remote-debugger/connect.

    1. Sign-in and environment. F&O Studio reads the selected environment's Dataverse URL, gets a Dataverse token and asks the environment for its finance and operations URL and application version.
    2. Find the proxy. xpp.debuggerProxyPath if set; else %LOCALAPPDATA%\Microsoft\Dynamics365\<application version>\FinOpsTools\DebuggerProxy\, then the same folder for the version of the active configuration.
    3. Write debug sources for your models and for standard elements with breakpoints, and copy the code view breakpoints onto them (Breakpoints and Source Mapping).
    4. Build the attach configuration: processName AXHost.exe, requireExactSource: false, a sourceFileMap that maps the compiler's source root (e:\source\) to the debug source folder, and symbolOptions with a module filter (loadOnlyIncluded) listing your packages' modules (Dynamics.AX.<package>.*.netmodule and .*.dll), the C# assemblies your projects reference, and the one module of each standard element with a breakpoint. Just My Code is left at the debugger's default (on), as Visual Studio does.
    5. Start the proxy inline. The arguments are the ones Visual Studio passes in its VSDbgLaunch.json:
    Microsoft.Dynamics.AX.DebuggerProxy.exe --port <free local port> --remoteProxyHost <environment host>
    --VSVersion vsdbg --accessToken <Dataverse token>

    F&O Studio picks a free port instead of the default 5119, so a Visual Studio session or a leftover proxy on that port does not stop it. It runs the proxy itself (a ProxyDebugAdapter) rather than as a plain executable, so the proxy's error output goes to the X++ output channel (prefixed [DebuggerProxy]) and its exit code is reported, instead of VS Code's bare "read error".

    The adapter changes a few messages on the way:

    Message Change Why
    initialize adapterID is set to clr vsdbg rejects VS Code's debug type xpp; clr is .NET Framework, as in Visual Studio's launch file
    setBreakpoints on a code view (xpp:) Answered by F&O Studio with the state of the breakpoint's copy vsdbg does not know the code view; the copy on the debug source binds
    setBreakpoints, breakpointLocations, source Debug source paths are replaced by the symbols' document names (xppSource://Source/<model folder>\<AxType>_<Name>.xpp) A local path mapped with sourceFileMap does not bind to those documents
    Messages from vsdbg xppSource names are turned back into the debug source files So VS Code can open them
    stackTrace response Frames in a debug source file point at the same line of the element's code view You see the stop where you set the breakpoint
    disconnect continue first if stopped; terminateDebuggee: false The environment serves every user

    Cloud-hosted and VHD¶

    When the active environment is local, the configuration provider does not start the xpp adapter. It converts the packages' PDBs to portable PDBs, writes the debug sources and starts one clr attach session per AOS process. See Debugging on Cloud-Hosted.

    Infolog¶

    A debug adapter tracker on both xpp and clr sessions reads output events. Infolog messages arrive there as <InfologMessage> XML, as in Visual Studio's Infolog window; F&O Studio parses them into the Infolog view.

    Limitations¶

    • Preview. The debugger is part of a preview extension. It was verified on a UDE (10.0.2790.108) and on a VHD (10.0.46, IIS and IIS Express). Cloud-hosted environments use the VHD code path but have not been tested.
    • The debugger only attaches. It cannot start the environment or a process.
    • On a UDE you debug the deployed code. Breakpoints in code you changed but did not deploy bind to the old lines, or not at all.
    • Breakpoints in an element only bind if the element was prepared when the session started. A breakpoint in a standard element you add during the session says "This element was not prepared for debugging when the session started; restart the debugger."
    • Stopping pauses the environment for everyone (see above).
    • There is no process list to pick from. On a UDE the process is AXHost.exe unless you set processName.

    Troubleshooting¶

    Symptom Cause Fix
    "Select the environment first: F&O Studio: Select Environment." No environment selected in this window Run F&O Studio: Select Environment…
    "Microsoft.Dynamics.AX.DebuggerProxy.exe was not found. Run F&O Studio: Connect to Environment, or set xpp.debuggerProxyPath." The FinOps tools for this version are not on this machine Run F&O Studio: Connect to Environment…, or set xpp.debuggerProxyPath
    "The environment did not return its finance and operations URL." The Dataverse environment is not linked to a finance and operations environment Check the selected environment
    "X++ debugging stopped: DebuggerProxy exited with code … See the X++ output for details." The proxy could not connect or stopped Check the X++ output. Sign in again (Connect to Environment…), check that the environment allows debugging, and that no firewall or proxy blocks wss://<environment>/___sidecar
    "Start X++ debugging from the Run and Debug view or F&O Studio: Launch Debugger." A debug adapter was requested without the preparation step Start the session again from Run and Debug or Launch Debugger
    Breakpoint stays hollow, "Waiting for the symbols to load." The module holding the code is not loaded yet Run the code once (open the form); see Breakpoints and Source Mapping
    Breakpoint never stops in code you just changed The environment runs the previously deployed build Deploy First when warned, or Deploy to Environment
    The environment stops responding for everyone The debugger is stopped at a breakpoint or paused Continue or disconnect
