    Extension Internals¶

    This page describes the TypeScript extension in src/: how it activates, which server processes it runs, how commands, views, webviews and language features are wired, and where each feature lives. It is for contributors and for anyone who wants to understand what happens behind a command.

    For the big picture, read Architecture first.

    Activation¶

    package.json declares:

    Field Value
    main ./out/extension.js (TypeScript compiled by tsc from src/)
    engines.vscode ^1.101.0
    activationEvents workspaceContains:**/*.rnrproj, onFileSystem:xpp, onStartupFinished
    capabilities.untrustedWorkspaces.supported false (the extension runs the compiler, the debugger and the metadata server)

    activate() in src/extension.ts runs these steps:

    1. Creates the output channels X++ (server logs, command errors) and X++ Build (compiler output).
    2. Restores this window's environment selection (initEnvironmentSelection) and repairs XPPConfig files written by older versions that lacked members Visual Studio requires (repairGeneratedConfigurations).
    3. Creates two XppServerClient instances: server and languageServer. Neither starts a process yet; each starts on its first request.
    4. Creates the builder (XppBuilder), the deploy state, the project and Application Explorer tree providers, the xpp: file system for the code view, navigation, pac commands, the version guard and the environment status.
    5. Registers webview panel serializers so the element designer, form designer and label editor tabs survive a window reload (src/webviewState.ts).
    6. Registers the MCP server definition provider for Copilot (registerMcpProvider).
    7. Registers the file system provider, the tree views xpp.project and xpp.aot (with drag and drop), and language providers for X++ documents: definition, references, hover, rename, document links and drop edits. It also registers a definition provider for C# documents that goes from C# to X++ code.
    8. Registers every command through one wrapper (see below), then the feature modules: database, Dynamics 365 tools, productivity, security, performance, upgrade readiness, integration, telemetry queries, Copilot Activity, trace analyzer, report designer, references, Go To, history, tests and Test Explorer.
    9. Starts watching for a project selected by an agent (activeProject.txt). When an agent selects a different project, the extension asks before it opens it, because opening reloads the window.

    deactivate() releases running debugger proxies.

    The two server clients¶

    src/serverClient.ts owns one XppVsCode.Server.exe process.

    • Start: on first use it reads the active environment, then spawns server/bin/XppVsCode.Server.exe --config <json> --allow-data [--project <rnrproj>] with a hidden window, and sends initialize.
    • Protocol: newline-delimited JSON-RPC 2.0 on stdin and stdout. Each request gets a numeric id and a timer. Stderr goes to the X++ output channel.
    • Timeouts: 180 seconds by default; trace analysis uses 600 seconds; data queries take a timeout from the caller.
    • Methods it exposes:
    Client method JSON-RPC method Used for
    bridge(action, body) xpp/bridge metadata actions (designers, code view, explorers, projects, labels, models, reports)
    lang(action, body) xpp/lang language features (completion, symbols, code lens, implementations, syntax check, search)
    data(action, body) xpp/data business data (browse, query, explain plan, cancel, connection test)
    trace(body), traceAction(...) xpp/trace .etl trace analysis and loading call tree children
    tool(name, args) tools/call the same agent tools Copilot uses, called by the extension itself
    • State: onDidChangeState fires starting, ready or failed. ServerStatus (src/serverStatus.ts) shows it in the status bar; clicking restarts the server.
    • Restart: restart() kills the process and rejects pending requests with a message that points to F&O Studio: Restart X++ Server. The next request starts a new process. The extension restarts both clients when the environment or xpp.project changes.

    server serves designers, the code view, explorers and most commands. languageServer serves code intelligence, so building an index never blocks a designer.

    Bridge action names are typed: BridgeAction in src/bridgeContract.ts is a union of every action the server registers, and every result is a BridgeResult (success, optional message, other members per action). See Bridge-Protocol.

    Commands¶

    All commands go through one command(id, handler) helper in extension.ts:

    • It counts the command in VS Code global state when xpp.usageStatistics is on (local only; see Usage-Statistics).
    • It catches errors, writes the stack to the X++ output channel, remembers the error for Report a Problem… (recordError), and shows the message with Show Log and Report Problem buttons.

    Many commands take an element argument. elementFromArg accepts (type, name) strings, an Application Explorer or project tree node, or an xpp: code view URI (editor context menu), so the same command works from every menu.

    package.json contributes 169 commands (category "F&O Studio"). See Command-Reference.

    Views and webviews¶

    UI Implementation
    Application Explorer (xpp.aot) AotTreeProvider in src/aot.ts
    Project view (xpp.project) ProjectTreeProvider in src/project.ts, solution helpers in src/solution.ts and src/references.ts
    Copilot Activity (xpp.activity) src/activity.ts, reads the MCP server's activity.jsonl
    Results view src/results.ts
    Security view src/security/
    Element designer src/elementDesigner.ts with media/element.*
    Form designer and preview src/designer.ts with media/formPreview.*
    Label editor src/labelEditor.ts
    Report designer src/reports/
    ERD and diagrams src/erd.ts, src/diagrams.ts
    Data panel and SQL panel src/database/
    Trace panel src/traceAnalyzer.ts

    Webviews set a Content-Security-Policy with a nonce from crypto.randomBytes. Panel state is kept in the page (data-xpp-state on <body>), so registerPanelSerializer can reopen designer tabs after a reload.

    The code view (xpp: documents)¶

    X++ code is not stored as files you edit directly. The code view is a virtual file system:

    • XppCodeFileSystem in src/codeView.ts serves xpp: URIs. readFile reads the element through the bridge; writeFile splits your text back into declaration and methods and saves them through the bridge.
    • src/xppSource.ts lays out the source like Visual Studio: the declaration without its closing brace, methods (stored indented by four spaces) inside the class body, then }. splitSource uses the original declaration to keep trailing comments and macros. It also maps compiler line numbers to document lines (compilerLineToDocumentLine).
    • When the environment changes, open xpp: documents that are not dirty refresh from the new environment.

    See XPP-Code-View.

    Language features¶

    src/codeIntel/providers.ts registers completion, signature help, document and workspace symbols, code lens, implementations, call and type hierarchy, hover, folding, syntax diagnostics, semantic tokens and formatting. Obsolete API warnings are in src/productivity/obsolete.ts. Each feature is a switch under xpp.codeIntelligence.* (src/codeIntel/settings.ts). They call languageServer.lang(...); the server's CodeIntel class answers actions such as symbols, members, implementations, code_lens, calls, subtypes, syntax, obsolete, labels and search_code.

    Navigation (definition, references, hover) is XppNavigation in src/navigation.ts. The formatter and folding are pure TypeScript (src/codeIntel/formatter.ts, src/codeIntel/folding.ts).

    Microsoft's X++ language server is not used: it only advertises document sync.

    Build, deploy, tests and debugging¶

    Feature Where Notes
    Build src/build.ts Runs LabelC, then xppc, then reportsc from PackagesLocalDirectory\bin; reads xppc's XML log into Problems (src/diagnostics.ts); converts PDBs to portable ones with the shipped Pdb2Pdb (src/portablePdb.ts)
    C# references src/dotnetReferences.ts Builds referenced C# projects with MSBuild and copies their output into the package bin folder, as Visual Studio does
    Best practice build.ts Runs xppbp.exe
    Build tasks src/tasks.ts Task type xpp, actions buildProject and buildModel
    Deploy and sync src/udeDeploy.ts, src/pac.ts The work is in core (deployPackages, syncDatabase)
    Deploy state src/deployState.ts Built versus deployed per environment and model
    Tests src/tests.ts, src/testExplorer.ts The runner is core's runTests
    Debugger src/debug.ts Debug type xpp; on a UDE, the FinOps tools' DebuggerProxy.exe (--VSVersion vsdbg) is the debug adapter; on a local AOS, the C# extension's debugger

    Cloud operations through core¶

    The extension imports @fno-studio/core only through src/core.ts, which re-exports core/dist. Two small adapters connect core to VS Code:

    • Sign-in: dataverseTokens in src/ude.ts is a core TokenProvider over VS Code's Microsoft account (vscode.authentication.getSession('microsoft', ...)), interactive or silent. When xpp.auth.clientId is set, the scopes include that app ID.
    • Cancellation: src/coreHost.ts turns a CancellationToken into an AbortSignal (abortSignalOf, withAbortSignal).

    Logs go to output channels through core's Log interface; progress goes to VS Code notifications through Progress. See Core-Library.

    Copilot integration¶

    • MCP server: src/mcpProvider.ts registers the definition "F&O Studio" for provider id xpp.mcp. It watches **/.xpp/agent-rules.md, xpp.project and environment changes, and fires a change so VS Code restarts the server with the new arguments.
    • Language model tools contributed by the extension itself (not the MCP server): xpp_open_element, xpp_run_tests and xpp_query_data (src/database/queryTool.ts). xpp_query_data runs in the extension's process, which holds the database credentials; the agent never sees them.
    • Agents: generated from scripts/agent-definitions.js into agents/*.agent.md and the chatAgents and chatInstructions contributions. Never edit the generated files; run npm run agents.
    • Checkpoints and scope: src/agentSession.ts writes agentSession.json; the MCP server enforces it. See Copilot-Checkpoints-and-Scope.

    Settings with machine scope¶

    Settings that point at programs the extension runs have machine scope, so a workspace cannot set them: xpp.pacPath, xpp.debuggerProxyPath, xpp.build.msbuildPath and xpp.trace.manifestFolder. xpp.project has window scope. See Settings-Reference.

    Adding something new¶

    You add Also do
    A bridge action Register it in the server's RegisterActions with the right WriteKind, add the name to src/bridgeContract.ts, run node scripts/check-bridge-actions.js
    An agent tool Register it in ToolRouter.RegisterTools and add its definition to server/Resources/Tools.json (the server refuses to start when they differ)
    A Copilot agent Edit scripts/agent-definitions.js, run npm run agents
    Something in core Keep vscode out; run npm run test:core
    A command Add it to contributes.commands and register it with the command() helper
