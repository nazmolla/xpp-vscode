    Agent Tools: Build and Data¶

    These agent tools close the loop after the agent changes code: build the model, run the best-practice checks, run the unit tests on the environment, list what changed in Git, create a deployable package, look at business data, and show the user an element in the editor. For the overview and the guarantees, see MCP-Agent-Tools.

    Tool Purpose Where it runs
    xpp_build Build a custom model like Dynamics 365 > Build: LabelC, xppc with cross-references, reportsc MCP server
    xpp_check_best_practice Run the X++ best-practice rules (xppbp) on a custom model MCP server
    xpp_package Create a deployable package (.zip) of custom models from their last build MCP server
    xpp_diff_changes List the elements of your models that changed in Git MCP server
    xpp_run_tests Run SysTest classes on the environment's cloud runtime VS Code extension
    xpp_query_data Run one read-only SELECT on the environment's business database VS Code extension
    xpp_open_element Show an element in the X++ code editor or designer VS Code extension

    The last three are VS Code language model tools: they are registered by the extension and don't exist when the server runs in another MCP host (MCP-Server-Outside-VS-Code). You can reference them in a chat prompt as #xppRunTests, #xppQueryData and #xppOpenElement.

    When the agent uses them¶

    • After every code change: xpp_build, then fix every error. A build is only successful when the result says BUILD SUCCEEDED.
    • Next to the build: xpp_check_best_practice, then fix what it reports or say why a warning stays.
    • After deploying: xpp_run_tests to run the tests against the deployed code.
    • For a code review or a pull request description: xpp_diff_changes, then xpp_read_object on each element.
    • Only when you ask for a package: xpp_package. It does not deploy anything.
    • While investigating behaviour: xpp_query_data, after you confirm the query.
    • When you ask to see code: xpp_open_element, never the metadata .xml file.

    The agent does not deploy or synchronize a UDE database with these tools. You deploy with Deploy-to-Environment.

    Before you start¶

    • An active D365FO configuration with its compiler tools in PackagesLocalDirectory\bin (xppc, LabelC, xppbp, reportsc, SyncEngine).
    • A custom model; builds, best practice and packages refuse other models.
    • Git for xpp_diff_changes: your models must be in a Git repository.
    • For xpp_run_tests: signed in to the unified developer environment and the code deployed (Run-Tests).
    • For xpp_query_data: database credentials (F&O Studio: Request Database Credentials on a UDE, or the local AxDB on a cloud-hosted or VHD environment; see Database-Access).

    xpp_build¶

    Builds a custom model exactly like Dynamics 365 > Build: compiles label files (LabelC), then X++ (xppc) with cross-references, then the reports (reportsc), and returns every error, fatal error and warning with element, method, line and message.

    Parameter Type Meaning
    modelName string Model to build. Default: the active project's model
    scope string model (default) or project: report only the diagnostics of elements in the active project (xppc still compiles the whole package)
    syncDatabase boolean Synchronize the database after a successful build where a local database exists. Default false 
    { "modelName": "ContosoExtensions", "scope": "project" }

    Steps, as Visual Studio does them:

    1. When the active project belongs to the package: build the C# projects and copy the assemblies the X++ project references into <package>\bin (Solution-View-and-CSharp-References).
    2. LabelC for every label file of the model, into <package>\Resources.
    3. xppc with -metadata, -compilermetadata, -modelmodule, -output=<package>\bin, -xmllog, -log, -appBase, -refPath, one -referenceFolder per reference folder plus the custom folder, and -xref with the configuration's cross-reference server and database.
    4. After a successful X++ build: reportsc compiles the reports to <package>\Reports.
    5. With syncDatabase=true: SyncEngine on cloud-hosted and VHD environments. On a UDE the result says the database is synchronized by deployment instead.

    Output:

    BUILD SUCCEEDED: ContosoExtensions in 41s - 0 error(s), 2 warning(s).
<one line per diagnostic, errors first>
Reports compiled to <custom folder>\ContosoExtensions\Reports.

    Identical diagnostics are listed once with a count ((x12)). At most 80 lines are listed; the rest are counted with the path of the xppc XML log (<package>\BuildLogs\Dynamics.AX.<package>.xppc.xml). A build also fails when xppc exits with an error or no assembly was written, and then the end of the log is shown.

    Builds take minutes. Logs are kept in <package>\BuildLogs.

    UI equivalent: Build-Project-and-Model, Compiler-Diagnostics.

    xpp_check_best_practice¶

    Runs the X++ best-practice rules (xppbp, the checks Visual Studio runs and partner code reviews use) on a custom model and returns every warning and error with element, member, line, rule moniker and message. Takes a minute or more.

    Parameter Type Meaning
    modelName string Model to check. Default: the active project's model
    scope string model (default) or project: only the active project's elements 
    { "modelName": "ContosoExtensions", "scope": "project" }

    Output: errors first, at most 80 lines, then ... N more.. The XML log is <package>\BuildLogs\Dynamics.AX.<package>.xppbp.xml.

    UI equivalent: Best-Practice-Checks.

    xpp_package¶

    Creates a deployable package (.zip) of custom models with the script Visual Studio's Create Deployment Package runs (RunPackageCreationAll.ps1 in PackagesLocalDirectory\bin), from their last build. It does not build and does not deploy.

    Parameter Type Meaning
    modelNames string[] Custom models to package. Default: the active project's model
    version string Package version in the form 1.0.0.0 (default) 
    { "modelNames": ["ContosoExtensions"], "version": "1.0.3.0" }

    Output: PACKAGE CREATED: <path of the zip> or PACKAGE FAILED (exit N)., then the packages and version, the reminder that the package contains the last build, and the end of the script's log. Packages are written to %LOCALAPPDATA%\XppVsCode\packages\<yyyyMMdd-HHmmss>.

    UI equivalent: Create-Deployment-Package.

    xpp_diff_changes¶

    Lists the elements of your models that changed in Git: uncommitted changes, and with baseBranch also what the current branch changed since it left that branch (added, modified, deleted, renamed).

    Parameter Type Meaning
    baseBranch string Branch to compare with, for example main. Omit for uncommitted changes only 
    { "baseBranch": "main" }

    Output:

    3 changed element(s) (uncommitted and since main):
- ContosoExtensions AxClass/ContosoOrderStatusService: modified (uncommitted)
- ContosoExtensions AxTableExtension/CustGroup.ContosoExtensions: added (on the branch)
- ...

    For every model folder under the custom metadata folder it runs git status --porcelain and, with a base branch, git merge-base HEAD <branch> and git diff --name-status on the model's path. Only Ax<Type>/<Name>.xml files count as elements. At most 500 are listed. If none of your models is in a Git repository, it says so.

    UI equivalent: Show-Changed-Elements, Review-My-Changes. Scenario: Scenario-Review-a-Pull-Request.

    xpp_run_tests¶

    Runs X++ unit tests (SysTestCase classes) on the connected unified developer environment's cloud runtime, the same way Visual Studio's Test Explorer does, and returns pass or fail per test with assertion messages and infolog.

    Parameter Type Meaning
    classes string[] Test class names. Omit to run every test class of the active project
    methods string[] Only these test methods of the given classes
    timeoutMinutes number How long to wait for results. Default 30 
    { "classes": ["ContosoOrderStatusServiceTest"] }

    Before it runs, VS Code asks you to confirm: "Run X++ tests on the environment. The tests run on the connected environment against the deployed code and may create test data there." The run's lines go to the X++ Tests output channel.

    Tests run against the code deployed to the environment. If the build is newer than the last deploy from this machine, the result starts with WARNING: and says to deploy and run the tests again. If the run fails, the result starts with TEST RUN FAILED: and the last lines of the log.

    The tool uses the same runner as the Run Tests command, in @fno-studio/core (runTests), with your Dataverse sign-in. See Run-Tests and Test-Explorer.

    xpp_query_data¶

    Runs one read-only T-SQL SELECT (or WITH ... SELECT) against the business database (AxDB) of the active environment and returns tab-separated rows.

    Parameter Type Meaning
    sql (required) string One SELECT statement
    maxRows number Rows to return, 1 to 500. Default 50 
    { "sql": "SELECT TOP 10 ACCOUNTNUM, CUSTGROUP FROM CUSTTABLE WHERE DATAAREAID = 'usmf'", "maxRows": 10 }

    Rules the agent is given: SELECT only (no INSERT, UPDATE, DELETE, EXEC, INTO); one statement; SQL names are the table and field names (for example CUSTTABLE.ACCOUNTNUM); filter per company with DATAAREAID in lower case; always add TOP or WHERE and select only the columns needed. Enum fields hold integers; RecId values come back as text.

    Every query needs your confirmation: VS Code shows "Run a read-only query on the environment database" with the SQL.

    Output:

    QUERY OK on <database> (35 ms, read-only).
10 row(s)
ACCOUNTNUM  CUSTGROUP
...

    (limit reached) marks a truncated result. Output over 20,000 characters is cut with a note to select fewer columns or rows. Errors come back as QUERY FAILED: .... Without credentials the answer is NO DATABASE ACCESS with the advice to run F&O Studio: Request Database Credentials.

    How it stays read-only: the extension's own server process refuses statements that are not a single read-only query, and runs it in a transaction that is always rolled back. That process is started with --allow-data; the MCP server Copilot starts can't reach business data, and the agent never sees the connection or credentials. See Database-Access and SQL-Query-Panel.

    xpp_open_element¶

    Shows an element to the user in F&O Studio's editor: classes, and the code of tables, forms, views, entities, queries and maps, in the X++ code editor (optionally at a method, with a line of code selected); other elements in their designer.

    Parameter Type Meaning
    objectName (required) string Element name, for example SalesFormLetter
    objectType string AxClass, AxTable, AxForm... Optional when the name is unique
    method string Method to scroll to (code editor)
    text string Code to select, for example the line with the bug; searched from the method on 
    { "objectName": "CustGroup", "objectType": "AxTable", "method": "find" }

    Answers: Opened <name> in the X++ code editor at line N. (with method ... not found or text not found notes), Opened <type> <name> in the designer., NOT FOUND: no element named <name>., or AMBIGUOUS: <name> exists as AxTable, AxForm; pass objectType. Without a method or text, non-class elements open in their designer. See Open-Element and X++-Code-View.

    How it works¶

    • xpp_build, xpp_check_best_practice and xpp_package pass their arguments to the bridge actions build, best_practice and create_package, implemented in BuildService (server/Ported/MetaModel/BuildService.cs). They run Microsoft's command-line tools from PackagesLocalDirectory\bin. C# references are prepared by ProjectReferences (server/Host/ProjectReferences.cs), which follows the same rules as the extension's src/dotnetReferences.ts.
    • xpp_diff_changes is ChangedElementsReport (ChangedElementsReport.cs), which runs git. The base branch name is validated before it is used.
    • xpp_run_tests is registered in src/tests.ts, xpp_query_data in src/database/queryTool.ts (readOnlyQuery in core/src/data/client.ts, server side DataQueryService), and xpp_open_element in src/goTo.ts. Their definitions are in contributes.languageModelTools of package.json.
    • These server tools run in order with other non-read tools; they are not ParallelRead.

    Limitations¶

    • Only custom models can be built, checked or packaged.
    • scope=project filters the diagnostics; xppc still compiles the whole package.
    • No database sync on a UDE from xpp_build: deploy the package instead (Synchronize-Database).
    • xpp_package packages the last build; it does not build first.
    • xpp_run_tests tests the deployed code, not your local build.
    • xpp_query_data is read-only and row-limited; it can't change data.

    Troubleshooting¶

    Symptom Cause Fix
    Pass modelName, or select a project with xpp_select_project. No model given and no active project Pass modelName or select a project
    Model '...' is not one of your custom models; only your own models can be built. The model is a reference model Build your own model
    scope 'project' needs an active project (xpp_select_project). No active project Select a project or use scope=model
    BUILD FAILED: building or copying the projects and assemblies ... references. A referenced C# project failed to build Fix the C# project; check xpp.build.msbuildPath
    BUILD FAILED: label compilation (LabelC) exited with N. A label file is invalid Open it in the Label-Editor
    version must look like 1.0.0.0. Wrong package version format Use four numbers
    Your models are not in a Git repository, so changes can't be listed. No Git repository Put your models under Git (Source-Control-for-X++)
    NO DATABASE ACCESS: ... No credentials for the environment's database Run F&O Studio: Request Database Credentials
    Test results don't reflect your change The build is not deployed Deploy, then run again (Deploy-to-Environment)
