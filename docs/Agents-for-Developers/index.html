    Agents for Developers¶

    F&O Studio's developer agents are Copilot personas for X++ work: building features, reviewing changes, tracking down errors, tuning performance, preparing upgrades, writing tests and reports, and releasing. Each one follows its own working method, uses the F&O Studio agent tools on the real metadata, and hands off to the next agent when its step is done. Four more agents (Solution Designer, Architect, Security & License, Integration) serve developers and functional consultants alike and are described here too.

    For how agents are picked, routed and kept under control, see Copilot Agents.

    Before you start¶

    • GitHub Copilot chat in agent mode, and F&O Studio connected to an environment so the xpp_* tools are available (Connect to Environment).
    • A D365FO project for agents that create elements: new elements are added to the active project (D365FO Projects).
    • For xppRunTests: a unified developer environment with your code deployed (Run Tests, Deploy to Environment).
    • For xppQueryData: database access (Database Access).
    • Recommended before an agent changes code: start a Copilot checkpoint and, for a narrow task, set a Copilot scope.

    Overview¶

    Agent Changes things? Use it to Hands off to
    F&O Developer Yes, with permission Build or change a feature Code Reviewer, Test Engineer
    F&O Code Reviewer No Review a branch, change or element Developer, Release Manager
    F&O Support No Find the cause of an error, stack, batch failure or trace Developer
    F&O Performance No Find why something is slow and how to fix it Developer
    F&O Upgrade Reviewer No Check models before a version update Developer
    F&O Test Engineer Yes, with permission Write and run SysTest unit tests Code Reviewer
    F&O Report Developer Yes, with permission Build or change SSRS reports, ER, print management Code Reviewer, Report Builder
    F&O Report Builder Yes, with permission Build a report from a scanned or sample document Code Reviewer, Release Manager
    F&O Workflow & Events Yes, with permission Build approval workflows and business events Code Reviewer
    F&O Release Manager Yes, with permission Checks, package, deploy and release summary Release Notes
    F&O Code Archaeologist No Explain unfamiliar custom code Developer
    F&O Solution Designer No Turn one requirement into a design Developer, Test Scenarios
    F&O Architect No Decisions across models, integrations, ALM Solution Designer
    F&O Security & License No Access, roles, license cost, SoD, gaps Developer
    F&O Integration Yes, with permission Entities, services, business events, integration errors Data Migration

    "Yes, with permission" means the agent changes things only after you explicitly allow it, and only in a development, sandbox or build environment, never in production. If it doesn't know the environment type, it asks and treats it as production until you answer. "No" agents are read-only: they recommend changes and offer the next agent.

    F&O Developer¶

    Builds and changes X++ features in your own models, the way an experienced D365FO developer would.

    How it works:

    1. Understands before writing. Reads the standard elements involved (xpp_find_object, xpp_read_object, xpp_get_form_layout) and finds a standard precedent with xpp_find_examples. Reads the xpp_get_guide topic for any kind of code it hasn't written in the session.
    2. Extends, doesn't copy. Prefers metadata extensions, Chain of Command, event handlers and extension methods. It copies standard code only when nothing is extensible, and says why.
    3. Plans first for anything beyond a small change: elements to create or extend, names with the model's prefix, labels, security. It confirms the plan with you when it creates several elements.
    4. Creates through the tools (xpp_create_object, xpp_update_object, xpp_create_label) and adds elements to the project. It never writes AOT XML by hand.
    5. Proves it works: xpp_build until there are no errors or warnings in its elements, xpp_check_best_practice, and xppRunTests when tests exist. It opens what it changed with xppOpenElement.

    Output: what it changed (element, member, why), the build and best-practice result, and what is left for you (deploy, database sync, security assignment).

    Example prompts:

    Add a field CreditHoldReason (string, 60) to CustGroup through a table extension in model ContosoExtensions,
and show it on the CustGroup form after the Description field.

    Wrap SalesFormLetter.run with Chain of Command: after next, write an info message with the number of
journals posted. This is a development environment; you may create the class.

    Create a SysOperation batch job ContosoPurgeOldLogs that deletes ContosoLog records older than 90 days.
Plan it first and wait for my OK.

    F&O Code Reviewer¶

    Read-only reviewer for X++ changes before a pull request is merged.

    How it works:

    1. Lists the changes with xpp_diff_changes (base branch main unless you name another) and reads each changed element.
    2. Runs xpp_check_best_practice and xpp_analyze_performance on the changed elements, xpp_find_deprecations when the model calls obsolete APIs, and xpp_analyze_security (op=gaps) for new menu items, forms and services.
    3. Checks by hand what the tools miss: CoC wrappers that don't call next, logic in the wrong layer, set-based operations that fall back to row by row, missing ttsbegin/ttscommit, hard-coded text instead of labels, missing find/exist, and your Team Rules in .xpp/agent-rules.md.

    Output: findings ordered by severity (Blocker, Major, Minor) with element and method, problem, impact and fix; then what is good and what it couldn't verify. No style nitpicks.

    Example prompts:

    Review this branch against main.

    Review the class SalesFormLetter_Contoso_Extension only.

    Review my changes against the develop branch and focus on performance and security.

    F&O Support¶

    Read-only troubleshooter for errors, call stacks, batch failures and traces.

    How it works:

    1. For a message, runs xpp_find_message_source with the text exactly as shown. For "Field '...' must be filled in." it lists the mandatory fields first: the platform raises that message, so it looks at the field and its data, not only code.
    2. Reads the raising method (xpp_read_object with methodNames) and its callers (xpp_find_references) to state the exact condition.
    3. For a trace, uses xpp_analyze_trace (errors with call stacks, slow requests). For a batch job, reads its history and the job's class.
    4. Checks the data or setup behind the condition: in the live environment through the Dynamics 365 ERP MCP server, or with xppQueryData on a development environment.

    Output: the cause (condition and where it is), evidence, the fix (setup, data or code) and how to verify it. If the cause is setup or data, it says so plainly.

    Example prompts:

    Users get "Field 'Customer group' must be filled in." when they create a customer from the sales order.
Where does it come from?

    Here is the call stack of a batch job that fails in SalesFormLetter: <paste the stack>. Why does it fail?

    Analyze C:\Traces\posting.etl and tell me which errors occur and where.

    See also Scenario: From Error Message to Fix.

    F&O Performance¶

    Read-only analyst that finds why something is slow and how to make it fast.

    How it works:

    1. For a trace (.etl), runs xpp_analyze_trace: slowest requests, hot methods, repeated queries, call tree.
    2. Runs xpp_analyze_performance on the classes, tables and forms involved and reads the flagged methods.
    3. Looks at the queries: indexes on the tables (xpp_read_object), row counts and plans (xppQueryData on a development environment).
    4. Proposes typical fixes: set-based operations, joins instead of nested loops, firstOnly, field lists, caching, OnlyFetchActive, batch parallelism, indexes.

    Output: findings ranked by expected gain: where, why it's slow (evidence), the fix, and how to measure it.

    Example prompts:

    Posting customer collection letters is slow. Analyze CustCollectionLetterCreate and the tables it reads.

    Here is a trace of the slow form opening: C:\Traces\custtable-open.etl. What takes the time?

    See also Analyze Performance, Analyze Trace and Scenario: Performance Tuning a Slow Process.

    F&O Upgrade Reviewer¶

    Read-only reviewer that checks whether custom models and ISV solutions survive a version update.

    How it works:

    1. Runs xpp_find_deprecations on each custom model: obsolete APIs used, CoC wrappers of changed or removed methods, extension collisions.
    2. Reads the affected standard elements to see what changed and what replaces the obsolete API (the SysObsolete message).
    3. Checks the model's dependencies (xpp_get_model_info) and ISV models for the same issues.
    4. Searches the release notes and deprecated-features lists with xpp_search_docs for the target version.

    Output: a readiness report per model: blockers, required changes, recommended changes, the replacement for each obsolete call, and the test focus for the update.

    Example prompts:

    We move to the next service update. Check model ContosoExtensions for deprecated APIs and broken wrappers.

    Which of our Chain of Command wrappers wrap methods that changed in standard?

    See also Upgrade Readiness and Scenario: Upgrade to a New Version.

    F&O Test Engineer¶

    Writes automated tests for X++ code and makes them pass.

    How it works:

    1. Reads the code under test and its dependencies, and the xpp_get_guide topic on the Acceptance Test Library (ATL).
    2. Creates test classes (SysTestCase, ATL entities and data) in a test model or the project's model, one test per behaviour, with clear arrange, act and assert.
    3. Builds (xpp_build) and runs them with xppRunTests; fixes failing tests or reports the bug they reveal.

    xppRunTests runs the tests on the environment against the deployed code, so deploy first.

    Output: the tests created, what each covers, the run result, and any bug found.

    Example prompts:

    Write SysTest tests for ContosoCreditHoldService.validate: a customer group with and without a hold reason.

    Run the tests of the project and fix the failing ones.

    See also Generate SysTest Class and Test Explorer.

    F&O Report Developer¶

    Builds and changes reports: SSRS (data provider, contract, controller, temporary table, design), Electronic Reporting and print management.

    How it works:

    1. Finds a similar standard report (xpp_find_examples) and reads its data provider, contract and controller (xpp_get_report_design for its datasets and layout). Reads the xpp_get_guide topic "ssrs".
    2. Decides between a new report and extending a standard one. Standard reports can't be changed in place: it duplicates the report, extends its temporary table and data provider, and routes through print management or the controller. It lists the elements it will create with why each is needed, and creates no extras (setup fields, label files, menu items, privileges) unless you ask or the report can't work without them.
    3. For SSRS, creates the temporary table, contract, data provider and controller when the report needs them (a Query dataset needs none), writes the precision design with xpp_set_report_design, checks it with xpp_render_report, adds the output menu item and privilege when users run it from a menu, and builds with xpp_build.
    4. For Electronic Reporting, explains the data model, model mapping and format to configure, and X++ only when ER can't reach the data.
    5. For print management, covers the document type, setup and code hooks when the report is a business document.

    Output: elements created, remaining steps (deploy reports, security, menu, print management setup), and how to test.

    Example prompts:

    Create a report ContosoCustGroupList that lists customer groups with their payment terms, run from a menu item.

    Add the customer's VAT number to the sales invoice without changing the standard report.

    See also Report Designer, Report Preview and Wizard: Report.

    F&O Report Builder¶

    Turns a scanned or sample document (cheque, purchase order, invoice, preprinted stationery) into a working SSRS report: the data chain and a precision design that matches the sample to the millimetre.

    How it works:

    1. Asks first what it can't see: preprinted stock or plain paper, paper size, whether it replaces a standard business document or is a new report, which data each field shows, the target model, and one or two ruler measurements of the real form to verify the scan's scale.
    2. Lists only the elements the report needs, each with a one-line reason. For a standard document: the copy of the standard report and one hook that routes to it (for cheques, a copy of the matching Cheque_XX report and a Chain of Command of ChequeController.determineReportMenuOutput; for invoices, purchase orders and confirmations, the print management registration). Anything more it proposes instead of creating.
    3. Measures the sample with xpp_measure_image: boxes, rules and text lines in mm from the sheet's top-left corner, with estimated font sizes.
    4. Builds the data side: copies the standard report into your model (xpp_set_report_design with duplicateOf) and extends its temporary table and data provider, or creates a Query or data provider data source for a new report.
    5. Writes the precision design with xpp_set_report_design: fixed textboxes at the measured positions, a tablix for line items, fonts that D365FO renders with, labels for captions. On preprinted stock it leaves out everything already printed.
    6. Renders and compares with xpp_render_report and xpp_compare_layout, moving items until each is within 0.5 mm (or your tolerance), then builds with xpp_build.

    Output: elements created or changed (and the ones it proposed but didn't create), the comparison result per field, and what you still do: deploy, print a test on plain paper held over the preprinted form, confirm on the real printer at actual size, print management setup, fonts this machine doesn't have.

    Example prompts:

    Build our cheque layout from C:\Scans\cheque.png. It is preprinted cheque stock, 8.5 x 11 in, cheque at the top.
Model ContosoReports. It replaces the standard cheque.

    Here is a scan of our purchase order form (A4, plain paper): C:\Scans\po.png. Make PurchPurchaseOrder print like it.

    See also Scan Overlay and Measure and Scenario: Report from a Scanned Document.

    F&O Workflow & Events¶

    Builds approval workflows and business events.

    How it works:

    • Workflow: finds a similar standard workflow (xpp_find_examples), then creates the status field, workflow category, type, approval, the submit and event handler classes, menu items and the form changes (WorkflowEnabled, data source, type). The Wizard: Approval Workflow in F&O Studio does most of this.
    • Business event: the event class, its contract, where to send it from, the category, and how consumers (Power Automate, Azure Service Bus, Event Grid) subscribe.

    Output: elements created, the remaining setup in the client (workflow configuration, business event catalog and endpoints), and how to test.

    Example prompts:

    Add an approval workflow to ContosoPriceChangeRequest: submit, approve, reject, with a status field on the table.

    Send a business event when a customer is put on credit hold, with the account number and the reason.

    See also Wizard: Business Event.

    F&O Release Manager¶

    Gets a change ready for deployment and deploys it where allowed.

    How it works:

    1. Runs the checks: xpp_build of every model to release, xpp_check_best_practice, xppRunTests, xpp_analyze_security (op=gaps), labels.
    2. Summarizes the changes (xpp_diff_changes) with their risk: data model changes needing database sync, security changes, integrations, upgrade risks.
    3. Creates the deployable package with xpp_package (the tool asks you first).
    4. Deploys and syncs only to development, sandbox or build environments and only with your permission. Production goes through Lifecycle Services or the Power Platform admin center by your organization's process.

    Output: a release summary: checks with results, changes and risk, package path, deployment steps and rollback notes.

    Example prompts:

    Prepare model ContosoExtensions for release: run all checks and create the deployable package.

    What in this branch needs a database sync, and what is the risk of deploying it?

    See also Pre-Deploy Checklist, Create Deployment Package and Scenario: Prepare and Ship a Release.

    F&O Code Archaeologist¶

    Read-only agent that makes unfamiliar custom code understandable.

    How it works:

    1. Maps the model (xpp_list_model_objects, xpp_get_model_info): what it adds and what it extends.
    2. Follows the entry points (menu items, CoC wrappers, event handlers, batch jobs), reads the code and traces callers with xpp_find_references.
    3. Finds dead code: elements and methods nothing references, obsolete calls (xpp_find_deprecations), copies of standard code that a newer extension point would replace.

    Output: what it does in plain words, how it hooks into standard, a Mermaid diagram of the main flow, risks, and clean-up candidates with evidence.

    Example prompts:

    Explain what model ContosoLegacy does and how it hooks into sales order posting.

    Which classes in ContosoExtensions are never referenced?

    See also Scenario: Onboard to an Existing Codebase.

    F&O Solution Designer¶

    Read-only agent that turns one requirement into a functional and technical design a developer can build and a consultant can test. It writes no code.

    How it works:

    1. Restates the requirement and the open questions; asks only what blocks the design.
    2. Looks for standard functionality first (xpp_search_docs, xpp_find_examples, the live environment): configuration beats code.
    3. For the gap, finds the extension points: the standard elements and methods (xpp_read_object, xpp_find_references, xpp_get_form_layout) and how standard solves similar cases.

    Output: a design document with Summary, Functional design, Technical design (elements with names, extension mechanism per change, data model, labels), Security (privileges, duties, license impact via xpp_analyze_security), Data migration and integrations, Test scenarios, Risks and open questions.

    Example prompts:

    Requirement: sales clerks must enter a reason when they change the customer group of a customer. Design it.

    Design a credit hold flag on customer groups that blocks sales order confirmation.

    See also Scenario: Build a Feature End to End.

    F&O Architect¶

    Read-only agent for decisions that span many requirements.

    It covers:

    • Models and packages: inspects the landscape (xpp_list_models, xpp_get_model_info) and recommends the split, dependencies and naming.
    • Build or buy: standard feature, configuration, ISV solution or custom extension, with the trade-offs.
    • Integrations: OData, data management, custom services, business events, dual-write; volumes, error handling and monitoring.
    • ALM and environments: branches, builds, deployable packages, environment types (UDE, sandbox, production) and how changes flow between them.
    • Quality attributes: performance at volume, security and licensing, upgradeability (xpp_find_deprecations).

    Output: context, options with trade-offs, the recommendation and why, risks, and the decisions the customer must make, with a Mermaid diagram when it helps.

    Example prompts:

    We have three custom models with circular dependencies. Propose a new model split.

    Should we integrate orders from our web shop through OData, data management or a custom service? About 20,000 orders a day.

    F&O Security & License¶

    Read-only analyst for security and licensing, from the metadata and, when available, the live environment.

    It uses xpp_analyze_security:

    op Answers
    access Which privileges, duties and roles reach a menu item, form or table
    license The license a role or menu item requires and what drives it
    placement Which standard roles a new duty or privilege belongs in
    gaps Menu items, forms and services of a model that no privilege covers
    sod Segregation-of-duties conflicts

    It reads users' actual role assignments in the live environment when needed.

    Output: the answer with the chain (role, duty, privilege, entry point, access level) and license impact; the cheapest license that still works.

    Example prompts:

    Who can open the CustGroup menu item, and with which access level?

    What license does TradeSalesClerk need, and what drives it?

    Find menu items in ContosoExtensions that no privilege covers.

    See also Security View, Analyze License and Find Security Gaps.

    F&O Integration¶

    Designs, builds and troubleshoots integrations.

    How it works:

    • Picks the entity: finds standard entities for the data (xpp_find_object, xpp_list_objects on AxDataEntityView), reads their fields, keys and whether they are public (OData) and enabled for data management. Prefers a standard entity, then an extension, then a new entity.
    • Builds: entity extensions or new entities with staging tables through the F&O Studio tools; custom services and business events when entities don't fit.
    • Troubleshoots: reads the import or OData error, finds its source (xpp_find_message_source), and checks the staging data and mappings in the live environment.

    Output: for design, the entity or service per data flow, keys, direction, volume, error handling; for errors, cause and fix.

    Example prompts:

    Which standard entity exposes customer groups over OData, and is it enabled for data management?

    Add our field CreditHoldReason to the customer group entity and its staging table.

    See also Try Data Entity (OData) and Scenario: Expose Data to an Integration.

    Tips¶

    • Name the environment type. "This is a development environment; you may create the elements." Without it, agents that change things ask, and treat the environment as production meanwhile.
    • Ask for the plan first on larger changes. The F&O Developer confirms its plan when it creates several elements.
    • Use the handoffs. Developer, then Code Reviewer, then Release Manager is the usual path.
    • Watch the work. Copilot Activity shows each tool call; a notification offers a diff after each element change.
    • Be able to undo. Start a checkpoint before the agent writes.

    Limitations¶

    • Read-only agents are read-only by instruction. To make the server refuse changes outside a set of elements, set a Copilot scope.
    • The F&O Studio tools write only to your own (custom) models; standard elements are changed through extensions.
    • xppRunTests tests the code deployed to the environment, not your local build.
