    Deploy to Environment¶

    Deploy Models to Environment uploads your packages, exactly as you built them on this machine, to your unified developer environment (UDE) and waits until the environment has applied them, optionally with a database sync. It is the equivalent of Visual Studio's Dynamics 365 > Deploy > Deploy Models to Online Environment and uses the same Dataverse API. Nothing is recompiled on the way, so the environment runs the build you debug. The Power Platform CLI (pac) is not needed.

    When to use it¶

    • After a successful build, so that the environment, the debugger, Run Tests, Run Snippet and the web client run your latest code.
    • When the project item in the Status Bar shows the cloud-upload icon (built after the last deploy).
    • After you changed tables or other synchronized elements, with a Module or Full database sync.

    Cloud-hosted and VHD environments do not need a deploy: their local AOS runs what you build. See Cloud-Hosted and VHD Environments.

    Before you start¶

    • A unified developer environment, connected on this machine and selected in this window (Connect to Environment, Select Environment).
    • Signed in with VS Code's Microsoft account to the environment's Dataverse (Sign In and Authentication). Your account needs the rights to deploy to the environment.
    • A built package. Only packages in your custom metadata folder with bin\Dynamics.AX.<package>.dll are offered. Build first (Build Project and Model). Packages linked into the metadata folder with a junction or symbolic link (for example by Open Team Repository) are offered too.
    • If your X++ project references C# projects or assemblies, MSBuild must be available; the deploy refreshes them in the package first.

    How to use it¶

    1. Start the deploy in one of these ways:
    2. Dynamics 365 view: Deploy > Deploy Models to Online Environment…;
    3. command palette: F&O Studio: Deploy Models to Environment;
    4. the Deploy now link in the tooltip of the project item in the status bar;
    5. Deploy First in the warning that Run Tests, the Debugger or Verify Changes in the Running App show when the build is newer than the deploy;
    6. Deploy after a passed Pre-Deploy Checklist.
    7. Pick the packages in Packages to deploy (as built on this machine). The list shows every built package with its folder; your project's package is preselected. You can select several.
    8. Pick the Database sync after deploy: | Option | Effect | |---|---| | None | No database sync. | | Module | Synchronize the tables of the deployed packages. | | Full | Synchronize the whole database (slow). |
    9. The X++ Deploy output opens and a notification "Deploying " shows each step. Typical output:
    Deploying ContosoExtensions to https://yourorg.crm.dynamics.com (database sync: Module)…
Packaging ContosoExtensions from <custom metadata folder>\ContosoExtensions…
Uploading ContosoExtensions_1_0_0_1_managed.zip (5120 KB)…
Deployment started (system job <id>). This usually takes several minutes, longer with the database sync.
  deployment: <status>
  deployment: <status>
Deployed.

    The status lines are the formatted status of the environment's system job; a new line appears when it changes. 5. When the deploy ends, the message "Deployed ." appears. The deploy is recorded for the models in those packages, so the status bar shows that the environment runs the latest build.

    Click Cancel on the notification to stop waiting. The message then says that the deployment keeps running on the environment, with its system job id.

    Deploy as a task¶

    The task { "type": "xpp", "action": "deploy", "dbSync": "Module" } deploys the active project's package without the pickers. See Build Tasks.

    Optional pac commands¶

    Deploy does not use pac. Two commands remain for teams that deploy with the Power Platform CLI themselves:

    • Sign In to Environment (pac) creates (or selects) a pac auth profile named after the environment's org.
    • Initialize Deployment Solution (pac) runs pac package init --package-type erp --model <models> in the workspace folder.

    Both are hidden on cloud-hosted and VHD environments. xpp.pacPath points at pac when it is not on PATH. See Power Platform CLI.

    Options and settings¶

    Setting Default Effect
    xpp.build.msbuildPath empty MSBuild used to refresh the C# projects and assemblies the X++ project references before the deploy.
    xpp.pacPath empty Path to pac, for the optional pac commands only.

    How it works¶

    The command is in src/pac.ts (PacCommands.deploy); the transport is in the core library, core/src/deploy.ts, reached through src/udeDeploy.ts. The flow was taken from what Power Platform Tools and pac do for Visual Studio's deploy.

    1. Refresh the project package¶

    For the open project's package only:

    • the C# projects and assemblies the X++ project references are built with MSBuild and copied into <package>\bin, as the build does (src/dotnetReferences.ts);
    • Windows PDBs in <package>\bin are converted to portable PDBs (Pdb2Pdb), because the UDE debugger reads portable PDBs only.

    If the references fail, the deploy stops before anything is uploaded.

    2. Check the environment¶

    F&O Studio checks that the Dataverse org has the solution msprov_fnouploadersolution. Without it the deploy fails with " has no Finance and Operations deployment support (solution msprov_fnouploadersolution). Is it a unified developer environment?"

    3. Zip each package¶

    Each package folder is zipped as <package>_1_0_0_1_managed.zip in %TEMP%\xpp-vscode-deploy\<timestamp> (deleted afterwards), with .NET's ZipFile as Visual Studio does:

    • every file under the package folder goes in as <package>/<relative path>;
    • left out: the BuildLogs folder, *.delete files and the build result logs (buildprojectresult.*, buildmodelresult.*);
    • a fnomoduledefinition.json at the root identifies the package for the environment's apply step, in the same shape pac and Visual Studio write:
    {
  "Module": { "Name": "ContosoExtensions", "properties": [{ "Item1": "packagingSource", "Item2": "Pipeline" }] },
  "BuildType": "Full",
  "PackageType": "Dev",
  "TimestampUtc": "<timestamp>",
  "CorrelationID": "<new GUID>",
  "ClientID": "<this machine's name>",
  "OrganizationID": "00000000-0000-0000-0000-000000000000",
  "DBSync": { "SyncKind": "Module", "Arguments": "" },
  "Versions": { "Platform": "0.0.0.0", "Application": "0.0.0.0", "Compiler": "0.0.0.0", "PackageVersion": "<from the current time>" },
  "AdditionalData": {}
}

    4. Upload through Dataverse¶

    For each package:

    1. POST msprov_fnopackages creates a package record: msprov_name (the zip name), msprov_buildtype 0 (Full), msprov_packagetype 0 (Dev), msprov_dbsyncoptions (None 0, Full 1, Module 2) and msprov_dbsyncvalue ({"Modules":["ContosoExtensions", ...]} for a Module sync, empty otherwise).
    2. PATCH msprov_fnopackages(<id>)/msprov_packagepayload uploads the zip. Files up to 100 MB go in one request; larger files use Dataverse's chunked upload in blocks of the size Dataverse returns.

    5. Start and wait¶

    POST msprov_deploypackagetofinopsasync with all package records starts the deployment as a Dataverse system job. F&O Studio reads the job (asyncoperations(<id>)) every 15 seconds and writes each new status to the output. The job succeeds when it is completed with status Succeeded; any other end fails the deploy with the environment's message. It waits at most 4 hours.

    6. Record the deploy¶

    After a successful deploy the models of the deployed packages (from their Descriptor files) are recorded as deployed for this environment, at the current time. See Status Bar for how this is compared with the last build.

    Why not pac package compile¶

    pac's own deploy path recompiles a scaffolded copy of your source with pac's SDK. Then the local build, and its portable PDBs, never reach the environment, and the debugger cannot match the code. F&O Studio uploads the built package folder instead, as Visual Studio does.

    Cloud-hosted and VHD environments¶

    There is nothing to deploy: the build writes into the local PackagesLocalDirectory and restarts the AOS hosts. The deploy commands are hidden there; if you start one anyway, the message is "This is a cloud-hosted or VHD environment: your models run on the local AOS once they are built, so there is nothing to deploy." To move code to a sandbox or production environment, create a deployable package (Create Deployment Package) and deploy it the way your project does.

    Limitations¶

    • UDEs only.
    • Deploys packages as last built on this machine; it never builds. A package that was never built is not offered.
    • Deploys made from Visual Studio, another machine or a pipeline are not recorded, so the status bar may still show the build as not deployed.
    • Cancelling only stops waiting; the deployment continues on the environment.
    • Not tested yet according to the release notes: several packages in one deploy and packages larger than 100 MB.

    Troubleshooting¶

    Symptom Cause Fix
    "Nothing to deploy: no package in ... has been built. Build your model first." No built package in the custom metadata folder. Build the model.
    "No environment selected." No environment in this window. Run Connect to Environment or Select Environment.
    "Not signed in to ." No Dataverse token. Sign in when VS Code asks; see Sign In and Authentication.
    "... has no Finance and Operations deployment support (solution msprov_fnouploadersolution)" The selected Dataverse org is not a UDE. Select the right environment.
    "Deploy stopped: building or copying the projects and assemblies the X++ project references failed." MSBuild or a copy failed. Read X++ Deploy; fix the C# project or set xpp.build.msbuildPath.
    "The deployment ended with status : " The environment failed to apply the package. Read the message; check the environment's deployment history.
    "Stopped waiting. The deployment keeps running on the environment (system job )." You cancelled. Wait for the environment; the deploy is not recorded, deploy again later if needed.
    "The deployment did not finish within 4 hours" Very long deployment or sync. Check the system job on the environment.
    POST ... returned 4xx/5xx: ... Dataverse refused a request (rights, limits). Read the error text; check your role on the environment.
