    Explain Plan¶

    Explain Plan shows how SQL Server would run a SELECT on the active environment's database, without running it. It compiles the query with SET SHOWPLAN_XML ON, then summarizes the plan in plain language: where the cost goes, scans of large tables, the indexes SQL Server says are missing, and plan warnings such as implicit conversions. Use it to check the SQL behind a slow while select before you change indexes or code. Visual Studio has no equivalent; there you would use the estimated execution plan in SQL Server Management Studio.

    When to use it¶

    • A form or batch job is slow and you suspect one query.
    • You found a heavy query with Database Performance Insights ("Most expensive queries") and want to see why it is expensive.
    • You want to know whether a new table index in your model would be used, before deploying it.
    • Analyze Performance or Analyze Trace pointed at a query and you want its plan on real data volumes.

    Before you start¶

    • Database access for the active environment. See Database Access.
    • An open SQL Query Panel with the query. Explain Plan accepts the same statements as a read-only run: one SELECT or WITH … SELECT.
    • Write the query in SQL, with SQL names. X++ select statements are not translated. To see the SQL an X++ query produces, take it from a trace (Analyze Trace) or from Query Store (Database Performance Insights).

    How to use it¶

    1. Open a query tab: F&O Studio: New SQL Query, Open as SQL in a Browse tab, or a Performance Insights query.
    2. Type or paste the SELECT. For example, the customers of a customer group:
    SELECT ACCOUNTNUM, PARTY, CUSTGROUP
FROM CUSTTABLE
WHERE DATAAREAID = 'usmf' AND CUSTGROUP = '10'
    1. Click Explain Plan on the toolbar.
    2. A progress indicator Getting the query plan shows in the status bar.
    3. A Markdown document opens beside the panel, as a preview tab. The query is not run.

    Reading the result¶

    The document has four parts:

    # Query plan (estimated; the query was not run)

    (the query)

Estimated cost 0.0328, 3 operator(s).

## Where the cost goes
- Clustered Index Scan on CUSTTABLE.I_10011RECID: 92% of the cost, about 1,240 row(s).
- Compute Scalar: 5% of the cost, about 1,240 row(s).
- Clustered Index Scan on CUSTTABLE.I_10011RECID reads about 1,240 rows: an index on the filtered columns may avoid it.

## Missing indexes
- Missing index on CUSTTABLE (impact 87%): equality [DATAAREAID, CUSTGROUP], inequality [], include [ACCOUNTNUM, PARTY]. In F&O, add it as a table index in your model, not in SQL.

## Warnings
None.

    The numbers and index names above are illustrative; yours come from your database.

    Part What it tells you
    Estimated cost, operators SQL Server's estimated subtree cost of the statement and the number of plan operators
    Where the cost goes The five operators with the highest own cost (their cost minus their children's), each with its physical operator, the logical one when different, the table and index, its share of the total cost and the estimated rows. Then every table scan, clustered index scan or index scan estimated to read more than 1,000 rows.
    Missing indexes Each index SQL Server's optimizer asked for: table, estimated impact, equality columns, inequality columns and included columns
    Warnings Plan warnings. Implicit conversions show the expression and a hint to compare with values of the column's type; a join without a join condition is called out as a cross join; other warnings show their name.

    When a part is empty it says "Nothing stands out.", "None suggested." or "None.".

    Acting on the result¶

    • Missing index. Do not create it in SQL: F&O Studio's insight text says the same, add it as a table index in your model. An index created directly in SQL is not part of your model and is not deployed with it. Add the index to the table in your model (or in a table extension), with the equality columns first, then build, deploy, synchronize and explain the query again.
    • Large scan. Look at the WHERE clause: is a filter missing in the X++ code, or does no index start with the filtered fields?
    • Implicit conversion. A value of another type is compared with the column, which can prevent an index seek. In SQL you wrote, quote strings and use numbers for numeric columns.
    • Cross join. A join condition is missing; in X++ check the exists join / join clauses and their where.

    Options and settings¶

    Explain Plan has no settings. It uses the Database Access of the active environment.

    How it works¶

    1. The panel sends a plan message with the editor's text (src/database/dataPanel.ts).
    2. DataClient.plan (core/src/data/client.ts) sends the plan action to the extension's server process (xpp/data) with the connection.
    3. The server (DataQueryService.cs) applies the read-only check (ReadOnlySql.cs), opens a connection, runs SET SHOWPLAN_XML ON, executes the query text (SQL Server returns the plan instead of running it) with a 60-second time limit, and turns SHOWPLAN_XML off again.
    4. QueryPlan.cs parses the showplan XML: StmtSimple/@StatementSubTreeCost for the total, each RelOp for operators (own cost = its EstimatedTotalSubtreeCost minus its child operators'), MissingIndexGroup for missing indexes and Warnings for warnings.
    5. The summary comes back; the raw XML is returned too when it is under 200,000 characters, but the document shows only the summary.
    6. The extension writes the Markdown document and opens it beside the panel.

    Limitations¶

    • Estimated plan only. Actual row counts, actual memory grants and runtime statistics are not shown, because the query is not run.
    • One SELECT at a time, with the same read-only rules as the query panel; no plans for UPDATE or DELETE.
    • No graphical plan. For the full plan, open the same query in SQL Server Management Studio (Open in SSMS).
    • The plan is the one SQL Server compiles for the literal values you wrote. X++ queries usually run with parameters, so the plan in production can differ.

    Troubleshooting¶

    Symptom Cause Fix
    "Only SELECT queries run in read-only mode." The text is not a SELECT Explain only SELECT statements
    "Run one statement at a time." More than one statement in the editor Keep one statement
    "The server returned no plan." SQL Server returned no showplan for the text Check that the text is a complete query
    "No database access. Request credentials with F&O Studio: Request Database Credentials, then run again." No credentials on a UDE Run Request Database Credentials
    The document says "Nothing stands out." The plan has no costly operator or large scan The query is probably not the problem; look at how often it runs (Analyze Trace)
