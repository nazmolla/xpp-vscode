    Bridge Protocol¶

    The bridge is how the F&O Studio extension talks to its metadata server. It is JSON-RPC 2.0 over the server's stdin and stdout, one message per line, with F&O Studio's own methods (xpp/bridge, xpp/lang, xpp/data, xpp/trace) next to the MCP methods Copilot uses (initialize, tools/list, tools/call). The xpp/bridge method calls a named action, such as read_object or set_element_property, and returns its JSON result.

    This page is for contributors and for people who script the server. Most users never see it.

    Transport¶

    • Framing: one JSON object per line, UTF-8 without BOM, \n line ends. The server strips \r and \n from every response, so a response is always one line.
    • Direction: the client writes requests to the server's stdin; the server writes responses to stdout. Stderr carries logs (timestamped lines), never protocol.
    • Ids: every request with an id gets exactly one response with the same id. Requests without an id (notifications such as notifications/initialized) get none.
    • Order: responses can arrive out of order. Read-only tool calls, xpp/data and xpp/trace run in parallel; match responses by id.
    • Timeouts: the extension waits 180 seconds per request by default (600 for trace analysis). The server itself does not time out requests.

    The extension's client is src/serverClient.ts; the server side is server/McpStdioServer.cs.

    Session¶

    sequenceDiagram
    participant C as Client
    participant S as XppVsCode.Server.exe
    C->>S: {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18"}}
    S-->>C: {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"tools":{}},"serverInfo":{...},"instructions":"..."}}
    C->>S: {"jsonrpc":"2.0","id":2,"method":"xpp/bridge","params":{"action":"find_object","body":{...}}}
    S-->>C: {"jsonrpc":"2.0","id":2,"result":{"success":true,...}}

    initialize answers with the protocol version the client asked for (default 2025-06-18), capabilities: { tools: {} }, serverInfo (name: "xpp-vscode") and the agent instructions.

    Methods¶

    Method Params Result Notes
    initialize protocolVersion, clientInfo server info and instructions
    ping none {}
    tools/list none { "tools": [ ... ] } definitions from server/Resources/Tools.json
    tools/call name, arguments { "content": [{ "type": "text", "text": ... }], "isError": bool } some report tools add image content (PNG, base64)
    xpp/bridge action, body the action's JSON metadata actions, below
    xpp/lang action, body JSON language features (CodeIntel)
    xpp/data action, body JSON only with --allow-data; actions test, browse, query, plan, cancel
    xpp/trace action, body JSON analyze, children, close

    Errors use JSON-RPC error objects: -32601 "Method not found" for unknown methods (and for xpp/data without --allow-data), -32602 "Unknown tool", -32603 "Internal error" with the exception message.

    xpp/bridge actions¶

    Request and result¶

    {"jsonrpc":"2.0","id":7,"method":"xpp/bridge","params":{"action":"get_element_properties","body":{"objectType":"AxTable","objectName":"CustGroup","path":["Fields","CustGroup"]}}}

    Every action returns an object with at least success (boolean) and, when it fails, message. The other members depend on the action. In TypeScript this is BridgeResult:

    export interface BridgeResult {
    success: boolean;
    message?: string;
    [member: string]: any;
}

    A failed action is a normal result, not a JSON-RPC error:

    {"success":false,"message":"AxClass 'Global' belongs to <model>, which you can't change. Create an extension in your model instead."}

    An unknown action returns {"success":false,"message":"Unknown action: <name>"}.

    Common body members: objectType (an Ax type such as AxTable, AxClass, AxForm), objectName, modelName, path (designer node path as an array of names), checkOnly.

    The contract¶

    src/bridgeContract.ts lists every action as a TypeScript union (BridgeAction, 80 names today). XppServerClient.bridge(action, body) only accepts those names, so a typo fails to compile.

    Two checks keep the contract and the server in step:

    • node scripts/check-bridge-actions.js reads the contract, the registrations in MetaModelBridgeServer.RegisterActions and the new MetaModel.BridgeAction(...) registrations in ToolRouter.cs, and every bridge call in src/. It reports actions listed but not served, served but not listed, and used by the extension but not served. npm run test:server and the release build run it.
    • A unit test in test/server checks the same against the running registry.

    Registration and dispatch¶

    Each action is registered once in MetaModelBridgeServer.RegisterActions (server/Ported/MetaModel/MetaModelBridgeServer.cs) as a BridgeAction (BridgeActions.cs):

    Member Meaning
    Name the action name in the contract
    Write WriteKind: Read, Edit, Create or Copy
    Handler takes the body JSON, returns the result JSON
    UsesMetadata true by default; false for cross-reference actions, which run without the lock

    Registering a name twice throws at startup.

    Dispatch(action, body):

    flowchart TD
    A["Dispatch(action, body)"] --> B{"registered?"}
    B -- "no" --> U["success:false, Unknown action"]
    B -- "yes" --> L{"UsesMetadata?"}
    L -- "yes" --> K["take the metadata lock"]
    L -- "no" --> R
    K --> R["WriteDenial(kind, body)"]
    R -- "denied" --> D["success:false, message"]
    R -- "allowed" --> H["Handler(body)"]
    H -- "exception" --> E["success:false, message = cause"]
    H --> OK["result JSON"]

    Write kinds and checks¶

    WriteKind Check before the handler
    Read none
    Edit EditDenial(objectType, objectName): an existing element must belong to a custom model. Skipped when checkOnly is true
    Create TargetModelDenial(modelName): the target model must be a custom model
    Copy same as Create

    In the MCP server process (started with --activity-log), Edit and Create actions also go through the Copilot session: AgentScopeDenial refuses elements outside the scope you set, and BeforeAgentWrite keeps the element's state in the open checkpoint. See Security-Model and Copilot-Checkpoints-and-Scope.

    Some actions are registered as Read but write non-AOT files (labels, models, project items, .axpp import). They apply their own checks: label writes go only under the custom metadata folder, and label file IDs and languages are validated before any path is built.

    Errors are unwrapped (MetaModelBridge.Cause) so messages show the real cause instead of "Exception has been thrown by the target of an invocation". The full exception goes to %TEMP%\XppVsCodeBridge.log.

    Agent tools over the same pipe¶

    tools/call goes to ToolRouter. Many tools delegate to bridge actions (for example xpp_create_object to create_object, xpp_build to build), so the same write checks apply to Copilot. With --activity-log, HandleToolCall snapshots the element before a WritesElement tool runs and appends an entry to activity.jsonl afterwards.

    The extension can call agent tools itself with XppServerClient.tool(name, args).

    Calling the server by hand¶

    Scripts in scripts/ start the server with a configuration and send one request. Always use them with a timeout; never leave a stdio session waiting.

    node scripts/bridge-call.js <exe> <config.json> find_object "{\"objectName\":\"CustGroup\",\"objectType\":\"AxTable\",\"exactMatch\":true}"
node scripts/tool-call.js <exe> <config.json> xpp_read_object "{\"objectType\":\"AxClass\",\"objectName\":\"SalesFormLetter\",\"methodNames\":[\"construct\"]}"

    <exe> is server\bin\XppVsCode.Server.exe; <config.json> is an XPPConfig file. bridge-call.js takes an optional maxChars; tool-call.js takes outBase (where images are saved) and maxChars.

    Adding an action¶

    1. Add the handler to the right service (see the roles in Metadata-Server).
    2. Register it in RegisterActions with the correct WriteKind. A write action registered as Read would skip the ownership check.
    3. Add the name to BridgeActions in src/bridgeContract.ts.
    4. Run node scripts/check-bridge-actions.js and npm run test:server.
    5. If behaviour of existing actions must not change, run the golden master before and after (see Testing-the-Extension).
