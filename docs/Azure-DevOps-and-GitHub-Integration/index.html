    Azure DevOps and GitHub Integration¶

    F&O Studio recognizes repositories hosted on Azure DevOps (Azure Repos) and GitHub from the origin remote of your Git repository, and uses that to link your work to Azure Boards work items and to open the repository's pipelines. The integration is deliberately light: it reads the remote URL, writes to VS Code's commit message box and opens web pages. It calls no Azure DevOps or GitHub API and needs no token. This page describes what is recognized, what each host supports and how it combines with the general Azure DevOps and GitHub setup of a D365FO team.

    When to use it¶

    • Your team tracks work in Azure Boards and wants commits and pull requests linked to work items.
    • Your code is on GitHub but your work items are in Azure Boards.
    • You want one click from VS Code to the team's build pipelines or GitHub Actions runs.

    Before you start¶

    • Git on the PATH, and the repository cloned on the machine.
    • The repository's origin remote pointing to Azure DevOps or GitHub (see the URL forms below).
    • Either the workspace folder or one of your custom models inside that repository (see How the repository is found).
    • For GitHub repositories with Azure Boards: the Azure Boards app for GitHub installed and the repository connected to the Azure DevOps project (general Azure DevOps setup, done by a project administrator, not by F&O Studio).

    What each host supports¶

    Feature Azure Repos GitHub
    Link Work Item… Adds #123 to the commit message Adds AB#123 (the Azure Boards mention for GitHub)
    Open Work Item… Opens https://dev.azure.com/<org>/<project>/_workitems/edit/<id> Not available: shows "The repository is on GitHub: open the work item from Azure Boards (AB# mentions link there)."
    Open Pipelines Opens https://dev.azure.com/<org>/<project>/_build Opens https://github.com/<owner>/<repo>/actions, filtered on the current branch
    Work items in Review My Changes #123 and AB#123 mentions in the branch's commit messages Same
    Change marks, Show Changed Elements, View History, xpp_diff_changes Any Git repository Any Git repository

    The last row does not depend on the host at all: every Git repository, wherever it is hosted, gets change marks, history and review.

    Recognized remote URLs¶

    F&O Studio reads git remote get-url origin and recognizes these forms (a trailing .git is ignored):

    Form Example
    Azure DevOps HTTPS https://dev.azure.com/contoso/FinOps/_git/ContosoFinOps
    Azure DevOps HTTPS with user name https://contoso@dev.azure.com/contoso/FinOps/_git/ContosoFinOps
    Azure DevOps SSH git@ssh.dev.azure.com:v3/contoso/FinOps/ContosoFinOps
    Older visualstudio.com HTTPS https://contoso.visualstudio.com/FinOps/_git/ContosoFinOps (also with DefaultCollection/)
    GitHub HTTPS https://github.com/contoso/contoso-finops
    GitHub SSH git@github.com:contoso/contoso-finops

    visualstudio.com URLs are turned into https://dev.azure.com/<org>/<project> for the links. Encoded repository names (for example %20 for a space) are decoded.

    Not recognized:

    • remotes other than origin (an upstream remote is ignored);
    • Azure DevOps Server (on-premises) and GitHub Enterprise Server host names;
    • ssh:// URLs.

    For those, the commands show "The workspace is not in a Git repository with an Azure DevOps or GitHub origin." The host-independent Git features keep working.

    How the repository is found¶

    The work item and pipeline commands look for a Git repository in this order and use the first one found:

    1. each folder of the current VS Code workspace (when a project is open: the project folder, the model folder and the C# project folders of its workspace);
    2. the real folder of each of your custom models (junctions resolved), so a model linked from the custom metadata folder into a repository is found even when the workspace is elsewhere.

    In each candidate F&O Studio runs git rev-parse --show-toplevel. Then it reads the origin remote of that repository. If your models live in several repositories, the first match wins; open the project whose folder is in the repository you want, so the workspace folder is found first.

    How to use it¶

    1. Clone the repository (VS Code's Git: Clone, or Open Team Repository… which also links and builds the packages; see Open Team Repository).
    2. Open your D365FO project. Make your change.
    3. Before you commit, run Link Work Item… from the command palette or the Dynamics 365 view (Deploy). Enter the work item number. The mention is added to the commit message and the Source Control view opens.
    4. Commit and push with VS Code's Source Control view.
    5. Create the pull request on the hosting site (or with an extension such as GitHub Pull Requests). Azure Repos and Azure Boards link the commits, and the pull request, to the work item from the mention.
    6. Run Open Pipelines to watch the team's build.

    Details and every prompt: Work Items and Pipelines.

    General Azure DevOps and GitHub practice for D365FO¶

    The following is common D365FO practice. F&O Studio neither sets it up nor needs it, but it works alongside it:

    • Branch policies on main (Azure Repos) or branch protection rules (GitHub): required reviewers, a successful build, linked work items. Azure Repos can require a linked work item on every pull request; the #123 mention from Link Work Item… links the commit to the work item. If the pull request does not show the work item, add it on the pull request page.
    • A build pipeline that compiles the models with the X++ compiler from Microsoft's NuGet packages and produces the deployable package; see Build Automation and Pipelines.
    • Release to sandbox and production through Lifecycle Services or the Power Platform admin center; see Environments and Promotion.
    • Azure Boards for GitHub: connects a GitHub repository to an Azure DevOps project so AB#123 mentions link.

    Options and settings¶

    There are no settings for the integration itself: the host is read from the remote each time a command runs. Review My Changes reads work item mentions from the commits between the base branch you enter (proposed from xpp.git.baseBranch, else main) and HEAD; with an empty base branch it lists no work items.

    How it works¶

    All of it is in src/devops.ts:

    • parseRemote(url) matches the remote against the forms above and returns the host kind (azure or github), the base URL and the repository name.
    • linkWorkItem() uses the API of VS Code's built-in Git extension (vscode.git) to find the repository whose root is the one found above (or the first repository) and appends the mention to its commit message box (inputBox). If the Git extension has no repository open, the mention is copied to the clipboard instead.
    • openWorkItem() and openPipelines() build a URL and open it with the system browser.
    • branchWorkItems(base) runs git log --format=%B <base>..HEAD and collects every #<number> and AB#<number> (up to nine digits, not preceded by a letter, digit, _ or &). src/review.ts uses it for the Work items line of the review.

    No credentials are read or stored. Browser pages use your normal browser sign-in.

    Limitations¶

    • No API access: F&O Studio cannot list, create or update work items, read their titles, create pull requests, or start or watch pipeline runs.
    • Work item links on GitHub depend on the Azure Boards app; F&O Studio cannot check that the connection exists.
    • Only the origin remote, and only dev.azure.com, *.visualstudio.com and github.com hosts.
    • Azure Pipelines opens the pipeline list of the project, not filtered on the branch.

    Troubleshooting¶

    Symptom Cause Fix
    "The workspace is not in a Git repository with an Azure DevOps or GitHub origin." No workspace folder or model folder is in a Git repository, or its origin is not a recognized URL. Run git remote get-url origin in the repository. Add or fix the origin remote, or open the project whose folder is in the repository.
    The mention lands in the clipboard, not in the commit box VS Code's Git extension has no repository open (for example Git is disabled in VS Code). Paste the mention into your commit message, or enable git.enabled and open the repository folder.
    The mention lands in another repository's commit box The Git extension has several repositories and none has the root found by F&O Studio; the first one is used. Open the workspace on the right repository, or copy the mention by hand.
    AB#123 does not link on GitHub The repository is not connected to Azure Boards. Ask an Azure DevOps project administrator to connect it (Project settings > GitHub connections).
    The wrong Azure DevOps project opens The origin remote points to another project. Check git remote -v.
